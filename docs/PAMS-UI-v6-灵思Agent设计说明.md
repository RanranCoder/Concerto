# V6 灵思 Agent 页面重新设计

日期：2026-10-14。状态：**原型已确认，正式页面已落地**。实施与验证见 [落地记录](PAMS-UI-v6-灵思Agent落地记录.md)。下文保留原型阶段的设计依据与审查范围。

入口是现有 [V6 原型设计 HTML](PAMS-UI-bright-v6.html?module=lingsi)。主导航中的“灵思”进入同一页面。页面引用 `PAMS-UI-v6-lingsi.css` 和 `PAMS-UI-v6-lingsi.js`，与排班考勤原型采用相同的扩展方式。

## 设计依据与取舍

核对了系统 README、现有 AgentHome、输入框、会话列表、过程区、工具与实体预览组件、Agent API 类型、后端工具实现，以及 V6 视觉规范和协作内聚方案。

灵思服务于活动筹备、排班考勤、内容宣传、组织资料、党务成员与日常事务。入口应以这些工作命名，专家编排呈现在过程里。用户无需另进协作页面或选择 P1–P4 等技术模式。

新任务时展示业务入口；开始任务后让结果占据主区域；预览成果时打开右栏。没有任务时不占用成果面板，不用统计卡填充首屏。

视觉沿用 V6：主操作 `#1668DC`、排班青绿、文书暖橙、少量灵思紫；白色工作面、浅灰任务栏、1px 边界，无额外渐变和大面积装饰。深色全部使用现有语义变量。字体沿用中文系统无衬线，任务正文 13px、辅助 10–12px，欢迎标题 26px。

## 信息结构

```text
系统主导航 │ 任务列表         │ 工作对话                 │ 成果预览（按需）
           │ 新建任务         │ 当前任务 / 状态           │ 内容 / 变更 / 来源
           │ 搜索与状态筛选   │ 用户要求与关联活动        │ 策划、文稿或排班
           │ 按时间分组       │ 执行过程与思考记录        │ 待补字段明确标注
           │ 任务名称与状态   │ 结果、草稿和确认清单      │ 对照阅读后回到对话
           │ 能力与资料范围   │ 输入框与本次运行模式      │
```

- 桌面任务栏 218–232px；对话正文最大宽度 800px；成果栏 350–402px。
- 1250px 以下成果改为抽屉，960px 以下任务列表也改为抽屉。
- 对话和成果分别滚动，输入区保留在底部。手机使用动态视口高度。
- 可见的“待确认”状态能直接跳到确认清单，避免在长对话中寻找按钮。

## 可审查的交互

| 场景 | 入口与关键动作 |
| --- | --- |
| 新任务 | 六类工作入口，点击只填入输入框，用户修改后发送 |
| 任务管理 | 搜索、全部/待确认/已完成筛选、时间分组、选中状态 |
| 活动策划 | 查看初稿和会务清单，核对六个章节与待补字段 |
| 排班 | 查看候选人员、空缺时段、草稿保存与后续发布提示 |
| 文稿 | 新闻稿初稿，未知主讲人、人数与现场事实标记待补 |
| 素拓 | “能力与资料范围”中打开加分示例，核对名单、每人分值和跳过项，确认后显示加分回执 |
| 资料问答 | 归档要求回答、引用片段、来源说明，以及资料不足空态 |
| 党务与成员 | 展示当前可查看的发展阶段汇总，不把其他角色权限当作默认权限 |
| 日常事务 | 按截止时间整理事项，回到活动签到、材料或已有策划任务 |
| 执行过程 | 默认折叠；可看专家角色、查询条件与结果、静态思考记录样例 |
| 待补信息 | 原型说明中打开“待补信息”，填写日期、时间、部门与人数；错误留在表单内纠正 |
| 确认与取消 | 清楚说明变更对象、范围和数量；取消后保留预览，支持重新核对 |
| 进行中、停止、失败 | 发送示例显示进行中；可停止、继续或重试；失败无成功回执 |
| 上下文 | “+”选择已有活动，可移除关联 |
| 模式 | 标准、只读、资料问答；只读和资料问答不启用自动协作，待确认写入按钮禁用 |

标准模式的确认入口只保留在对话中，成果栏“本次变更”用于核对，避免两个确认按钮产生不一致。排班空缺与素拓跳过项在确认和完成后继续显示。

## 业务边界与落地前待评估项

1. 策划工具写入 `activity_plan(DRAFT)`，稿件工具写入 `Article(DRAFT)`；草稿不等于提交审核或发布。原型中的会务清单只是建议，不隐式生成活动任务。
2. 素拓工具 `previewCreditBatch` 先进行 dry-run，确认后通过 `CreditService.batchAddFromActivity` 写入台账。原型遵循这一流程；展示分值为样例。
3. 现有 `generateActivitySchedule` 在确认前给出日期、时段、部门和人数条件，确认后才匹配具体人员并生成草稿。**原型中的“确认前查看候选人员与空缺”是新增设计提案**：落地前需决定增加无写入预计算，或者退回参数清单、把具体名单移到生成回执。此次没有改变后端行为。
4. 任务历史的筛选和状态当前为本地示例。落地时应核对会话、待确认计划和任务实体的状态关联，避免仅根据会话标题或前端临时状态推断。
5. 预览来源、材料正文、专家事件、思考记录与工具下钻应使用现有真实接口。思考及工具入参只展示后端实际提供的数据，沿用现有敏感级别处理；原型的静态样例不冒充真实模型过程。
6. 当前原型固定使用培训班样例。任意输入、补充消息与表单用于审查交互，不代表模型已经理解并生成新内容。示例确认只改变内存状态，刷新恢复。

## 审查顺序

先看新任务首屏，再打开“准备培训班策划初稿”，预览正文、展开过程、核对变更并确认或取消。随后检查“安排培训班活动值班”的空缺提示、资料问答的来源，以及三种模式的能力范围。右上角的原型说明提供待补信息、失败和资料不足示例。

切换顶栏明暗主题，在手机宽度检查任务列表与成果抽屉。用户确认原型后，再进入 React 组件、接口映射和业务流程的落地阶段。
