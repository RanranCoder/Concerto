# PAMS 灵思 UI 改版方案 v2

> 参考对象：**Trae Work**（AI 编程工作台）会话页
> 目标：把灵思从「聊天气泡」升级为「AI 工作台」——内容优先、产物分屏、模式就近可控
> 状态：设计稿（未落代码）。原型见 `docs/lingsi-ui-v2-prototype.html`

---

## 0. 一句话结论

灵思现在的 UI 是**对的骨架 + 错的装饰**：三栏（会话/对话/抽屉）、过程区+结论区两段式、拟执行清单卡这三件事都做对了，方向和 Trae 一致。

差距集中在三点：

| # | 差距 | Trae 的做法 | 灵思现状 |
|---|---|---|---|
| 1 | **AI 消息是"消息"还是"文档"** | AI 回答直接是页面上的文档流，无气泡无边框 | `.lingsi-bubble` 带 1px 边框 + 底色 → 卡片套卡片 |
| 2 | **产物能不能就地打开** | 对话里的文件 → 右侧面板分屏，对话不被遮挡 | 只有 Drawer 遮罩（全文预览、能力清单），打断对话 |
| 3 | **运行模式放哪** | 权限档位/模型/附件全收在输入框底栏 | 模式信息散在消息底部 MetaBar；没有"只读/可写"档位 |

**这三条不是审美问题，是交互模型问题。** 改完灵思的定位会从"能聊天的助手"变成"能干活的工作台"。

## 1. Trae Work 设计语言解剖（十条）

逐条从截图中读出的可复用规则，附"为什么"。

### 1.1 视觉层

| # | 规则 | 具体表现 | 为什么 |
|---|---|---|---|
| 1 | **灰阶极简** | 白底 + #f7f7f8 浅灰面板 + 深灰字，全页只有 3 处彩色：diff 的 ±绿红、文件类型图标色、发送按钮 | 让"内容"是页面上唯一的高对比元素；彩色一旦多处出现，注意力就被稀释 |
| 2 | **层级靠边框+间距，不靠阴影** | 卡片 1px `#e8eaed` 描边，圆角 8–10px，几乎无 box-shadow | 阴影在密集布局里会互相污染，出现"灰糊"层叠 |
| 3 | **小字号 + 适中密度** | 正文 13–14px，辅助 11–12px，行高 1.6–1.75；列表项 28–32px 高 | 单位面积信息量最大化，且中文长文仍可读 |
| 4 | **代码块自带语言标签与复制按钮** | 块顶左侧小号灰字 `Bash`，右侧一个 borderless 复制图标 | 复制的可达性决定了用户还要不要手动选文本 |
| 5 | **可折叠摘要头** | `1 个文件已更改 +5 -9 ▾` 一行，展开才是文件明细 | 默认给结论、按需给细节——这是"信息密度自适应" |

### 1.2 交互层

| # | 规则 | 具体表现 | 为什么 |
|---|---|---|---|
| 6 | **用户消息 = 引用块，不是气泡** | 用户输入是左对齐、浅灰底、1px 描边的**块**，近乎满宽 | 长 prompt 在 76% 宽气泡里会折成多行、起点不齐；引用块读起来像"工作记录" |
| 7 | **对话里的一切产物可点开成分屏** | 点文件行 → 右侧面板打开该文件（带 tab 可并列） | **不打断对话就能看细节**。遮罩弹层要"关掉才能继续聊"，分屏不用 |
| 8 | **单侧控制点（Single Control Surface）** | 输入框底栏：`+` / 权限模式`完全访问▾` / 模型`DeepSeek-V4▾ + Max` / 发送 | 运行参数是**每次任务都可能变**的，放设置页等于让用户来回跳。就近控制 |
| 9 | **左栏是"任务"，不是"聊天记录"** | `新建任务`置顶 + 项目分组折叠 + 任务项两行（标题/元信息）+ 选中左侧竖条 | "任务"心智允许并行、允许有状态（跑着/待确认）；"聊天记录"只有时间序 |
| 10 | **免责声明常驻** | 每条 AI 回复右下角 `由 AI 生成`，11px 灰字 | 合规与预期管理，且不占视觉权重 |

## 3. 改版方案

### A. 布局：两栏 → 三栏（新增产物分屏）

```
┌──────────┬───────────────────────────────┬──────────────────────┐
│ 任务栏    │ 对话区                          │ 实体面板（可收起）      │
│ 252px    │ flex:1  ·  内容最大宽 760px      │ 452px                │
│          │                               │                      │
│ 新建任务  │  用户引用块                     │  [活动] [名册]  ×      │
│ ───────  │  ───────────────              │  ─────────────────    │
│ 今天 (3)  │  灵思：过程折叠条                │  活动详情              │
│ ▸ 任务A   │        文档流正文 + 表格          │  ─────────────────    │
│   任务B   │        引用 chip ──────────────►│  任务条线表             │
│ ───────  │        产物卡 ─────────────────►│  本次写入摘要           │
│ 更早 (12) │  ───────────────              │                      │
│          │  [ 输入框 · 单侧控制点 ]          │                      │
└──────────┴───────────────────────────────┴──────────────────────┘
```

**关键判断**：灵思的"产物"不是文件，是**党务实体**（活动 / 策划书 / 材料 / 名册 / 排班表 / 正文）。所以右栏叫 **`LingsiEntityPanel`（实体面板）**，不是"代码面板"。它的内容可以直接复用现有业务页的展示组件（活动详情、材料预览、名册表格）。

**为什么值得做**：现在看"将写入的正文"要开 720px Drawer，遮罩罩住整个对话，用户看完只能关掉。改成右栏后，**对话与产物可以对照阅读**——用户一边看清单卡一边看正文，确认决策质量直接提升。这是本次改版**收益最高的一条**。

### B. 消息区：去气泡化

**B1. 用户消息 → 引用块**

```
现在：                              改后：
                          ┌──────────────────────────────────┐
   ┌───────────────┐      │ 帮我把开班仪式的活动任务都生成出来， │
   │ 帮我把开班仪式  │      │ 名单以最新导入的为准。      [⧉] [✎]│
   │ 的活动任务都生  │      └──────────────────────────────────┘
   │ 成出来…        │       · 左对齐、满宽、浅灰底 + 1px 描边
   └───────────────┘       · hover 露出「复制」「编辑并重新发送」
   右对齐红底气泡             · 与 AI 文档流同栏 → 读作"工作记录"
```

去掉红底的理由：品牌红在灰阶体系里是**最高对比色**，用在每一条用户消息上会让红色失去"强调"语义（选中竖条、发送按钮、不可逆警示也用它）。红色**收窄到 4 处**：新建按钮图标、选中竖条、发送按钮、引用 chip 的 hover 描边。

**B2. AI 消息 → 文档流**

去掉 `.lingsi-bubble` 的 `border` 与 `background`，`.lingsi-outcome` 保留 24px 头像 + 11px 间距，消息间距 26px。理由：现在清单卡的边框套在气泡边框里，是两层同色描边——正是 §1.1 规则 2 说的"层叠污染"。

### C. 新增组件：`LingsiArtifactCard`（产物卡）

对应 Trae 的"1 个文件已更改"。**这是灵思最缺的一块**。

现在的执行回执是一行绿字（`.lingsi-notice`）：

```
41 条任务已写入「开班仪式」，38 人已分配。
```

改后：

```
┌──────────────────────────────────────────────────────────┐
│ ✓  2 项变更已产生              +41 任务  +38 成员      ▾  │
├──────────────────────────────────────────────────────────┤
│ [活] 开班仪式 · 活动任务   第四十期培训班 / 41 条     ↗  │
│ [册] 应签名单 · 组别回填   38 条记录                 ↗  │
└──────────────────────────────────────────────────────────┘
```

| 规格 | 值 |
|---|---|
| 容器 | 1px `--border` + `--r-md` + 白底，无阴影 |
| 摘要头 | 20px 圆角图标（成功绿底）+ 主文案 12.5px/500 + 右侧统计（等宽字体，`+` 用 `--ok`）+ 折叠箭头 |
| 明细行 | 20px 彩色方块（实体类型首字：活/册/文/报）+ 名称 + 灰字副行 + hover 露出「↗ 在右侧打开」 |
| 默认态 | **展开**（只 2–4 行，折叠反而增加一次点击）；> 6 行时默认折叠 |
| 点击行 | → 右栏打开该实体 |

**数据来源**：需要后端在 `AgentTaskDone` / 工具结果里回传结构化的变更摘要（实体类型、ID、名称、变更条数），而不是现在拼好的一句话。**这是本方案唯一必须动后端的点**（见 §6）。

### D. 过程区：视觉减重

现在的药丸头（border + 999px 圆角 + `--surface-strong` 底）在灰阶体系里偏重。改为**无边框的纯文字摘要行**：

```
现在：  ( ▸ 已完成 · 调用 3 项能力 · 耗时 0.9s )     ← 药丸，有边框有底色
改后：    ▸ 已完成 · 调用 3 项能力 · 耗时 0.9s       ← 11.5px 灰字，仅左侧小三角
```

进行中时：左侧三角换成 11px 旋转环（红色），文字 `正在思考…`，颜色提到 `--text-2`。
展开后的时间轴行：工具名用 `--text-2`，耗时右对齐（`tabular-nums`），左侧竖线降到 `--border-soft`。

保留"有失败项时不自动折叠"（§原方案 3.5.3 规则 4）——这条是对的。

### E. 输入区：单侧控制点（本方案第二高价值改动）

```
┌────────────────────────────────────────────────────────────┐
│ 帮我编写方案、核对名册、起草通知等党务工作…                    │
│                                                            │
│ [+]  [🔒 只读模式]  [✓ 标准模式]  [DeepSeek V3 ▾]      [➤] │
└────────────────────────────────────────────────────────────┘
 Enter 发送 · Shift+Enter 换行        灵思回答基于你的权限范围…
```

| 元素 | 作用 | 优先级 |
|---|---|---|
| **只读 / 标准模式切换** | 一键降档：只读模式下编排层**不挂载任何写类工具**，用户"就问一下别动数据"时不会每次都被清单卡打断 | **P1（收益最高）** |
| 模型标识 | 当前 provider 常驻可见（含「规则模式」降级态），替代现在消息底部的重复展示 | P0 |
| `+` 上下文/附件 | 预留位（一期可只做占位，或接"选择活动/材料作为上下文"） | P2 |
| 发送按钮进框 | 现在是 antd 默认 Button 摆在框外，视觉割裂 | P0 |
| 框下提示行 | 左：快捷键；右：权限说明（沿用原方案 §3.1 的文案） | P0 |

**只读模式的语义边界（必须写清楚）**：它**不是**权限降级，而是**工具可见性开关**——用户本来就有的权限不变，只是本次会话主动放弃写能力。实现上等价于 §原方案的"工具可见性过滤"，按 `mode` 参数过滤掉 `write=true` 的工具。这样不会引出新的越权风险。

### F. 左栏：会话 → 任务

| 改动 | 规格 |
|---|---|
| 新建按钮 | 右上角 `+` → 顶部**整宽描边按钮**「新建任务」+ `Ctrl N` 快捷键提示 |
| 分组 | 「今天 / 更早」按 `updatedAt` 本地分组，带可折叠三角 + 右侧计数 |
| 会话项 | 两行：标题（12.5px）+ 副行（`3 分钟前 · 5 步操作`，11px `--text-3`）；待确认徽标保留 |
| 选中态 | 白底 + 极淡投影 + **左侧 2.5px 红色圆角竖条**（现在只有红底，没有竖条，与原方案 §3.3 不符） |
| 搜索 | P2，一期不做 |

> 命名从"会话"改"任务"是**文案层改动，不改数据结构**——`agent_conversation` 表不需要动。但产品语义确实变了：副行显示"N 步操作"会让用户感知到这是有进度的工作单元。

### G. 消息动作行（P2）

AI 消息 hover 时光标处浮现：复制 / 有帮助 / 重新生成，最右 `由灵思生成`（11px `--text-3`，**常驻**，不参与 hover 显隐）。

原方案 §3.5.1 已规定"重新生成仅对最后一条消息显示"——这条保留。灵思的实际使用是**长任务会话**，重新生成的价值低于 Trae（代码场景），所以排 P2。

### H. 视觉 token：红色的收窄

| 保留红色的位置 | 理由 |
|---|---|
| 发送按钮 | 唯一的主行动 |
| 左栏选中竖条 | 定位当前任务 |
| 不可逆操作警示（清单卡头部、`.lingsi-plan` 边框） | 安全语义，必须醒目 |
| 引用 chip hover 描边 | 交互反馈 |

| 移出红色的位置 | 改为 |
|---|---|
| 用户消息底色 | `--bg-soft` + 1px 描边 |
| AI 头像底 | **保留**（品牌识别符号，24px 面积小、不构成噪声） |
| 过程区药丸边框 | 移除边框 |

## 6. 需要后端配合的两点

| # | 需求 | 位置 | 工作量 |
|---|---|---|---|
| 1 | `POST /api/agent/chat` 与 `/tasks/{id}/confirm` 增加 `mode` 参数（`readonly` / `standard`），编排层据此过滤 `write=true` 的工具 | `AgentOrchestrator` / `ToolRegistry` 的可见性过滤链路 | 小。**注意**：过滤必须发生在**工具可见性**层（已有三层防护的第一层），不能只在前端隐藏 |
| 2 | 工具结果 / `AGENT_TASK_DONE` 事件回传结构化 `artifacts[]`：`{entityType, entityId, name, deltaLabel, path}` | `ToolResult` 扩展 + `NotificationEventListener` 的 WS payload | 中。需要给 10 个写类工具逐个补 artifact 描述 |

### 9.11 第四轮（v2.4）：字符级流式渲染

二期预留的 `MESSAGE_DELTA` 契约正式启用。**跨三层改造，但接口零破坏** —— 前端事件枚举里早就留着这个类型，编排器只是多了一层回调。

| 层 | 实现 |
|---|---|
| `LlmProvider` | 新增 `chatStream(request, onDelta)`，**默认实现回退到非流式**（整段一次性回调）—— Stub 等不支持 SSE 的实现零改动接入，编排器不需要关心"这个 provider 会不会流式" |
| `DeepSeekProvider` | 走 JDK `HttpClient` 读 SSE 逐行（RestClient 会把响应整体缓冲，拿不到流）；`buildBody()` 抽出与 `chat()` 共用，避免两条路径字段漂移；**tool_calls 的 `id/name/arguments` 按 `index` 分片拼装** —— arguments 是逐字符到达的 JSON 文本，拼错不抛异常，只会表现为"参数校验拒绝"，极难查 |
| 编排器 | `callLlm(..., round)`：增量按 **round** 推送。**round 取值规则是本方法最重要的细节** —— 前端遇 round 变化就清空已拼装回复，所以每次"重新生成一段文本"都必须换 round：重试 → `round+1000`，降级 → `round+2000`（前一次可能已经吐了半截） |
| 合并 | `DeltaBatch`：**长度 24 字符 或 60ms** 双阈值合并 —— DeepSeek 按 token 吐，一次回答几百上千片段，直接透传会把 STOMP 连接与前端渲染都打爆 |
| 前端 | `applyStreamEvent` 的 `MESSAGE_DELTA` 分支：增量写进最后那条"进行中"占位的 `reply`；REST 返回用权威全文覆盖 |

顺带修了一个被流式放大的老问题：**自动滚动原来是无条件置底**，平时无所谓，字符流高频触发后会把"往上翻看过程"的用户一次次拽回来。改为距底 <120px 才跟随。
