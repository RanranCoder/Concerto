## 1. 设计语言基线（从现有代码提取，不新造）

这一节是后面所有页面设计的**约束来源**，全部来自源码核对，不是主观偏好。

### 1.1 颜色与表面

| 令牌 | light | dark | 用途 |
|---|---|---|---|
| `--color-red` | `#DE2910` | 同 | 品牌红：图标、强调、用户气泡、（A 股惯例）正向 |
| `--color-red-soft` | `rgba(222,41,16,.14)` | 同 | 今日列底色、hover 底、选中态底 |
| `--color-text` | `rgba(17,24,39,.92)` | `rgba(240,244,250,.94)` | 正文 |
| `--color-text-secondary` | `rgba(17,24,39,.6)` | `rgba(240,244,250,.55)` | 辅助文字、时间戳 |
| `--surface` | `#f7f8fa` | `#1b1e26` | **卡片底（实底，非透明）** |
| `--surface-strong` | `#fbfcfe` | `#23262f` | 表头、次级容器 |
| `--surface-border` | `#e4e8ef` | `#2e313a` | 1px 描边 |
| `--radius-lg` / `--radius-md` | `16px` / `12px` | 同 | 卡片 / 子块 |
| `--easing` | `cubic-bezier(.22,1,.36,1)` | 同 | 所有过渡 |

**关键事实**：`.glass-card` 的 background 是 `var(--surface)`，**是实底不是半透明**（"glass" 是命名，不是 `backdrop-filter`）。只有登录卡片用了真 `backdrop-filter`。因此灵思的容器**沿用 `.glass-card` 即可**，不要自己加模糊——否则暗色下会出现"灰糊"层叠。

**禁止事项**（源码已踩过的坑，文档化）：

- ❌ **不要用 `var(--color-red)` 拼 alpha 后缀**（如 `var(--color-red)55`）。CSS 变量替换是 token 级的，不会合并成 8 位 hex，渐变/阴影会直接失效。需要透明色时**写字面量 8 位 hex**，参考 `Dashboard.tsx` 的 `CARD_ACCENT` 注释。
- ❌ 不要在卡片上叠加多个 `box-shadow`；`.glass-card` 已有 `--surface-shadow`，`hover` 只改 `border-color`。
- ✅ 需要"更深一层"的容器时，用 `--surface-strong`，不要用透明度。

### 1.2 灵思的识别符号

现有 `MainLayout` 侧栏用 `/hello-kitty.png` 作为系统 logo，**灵思不能复用**（会让"系统"与"助手"两个身份混在一起）。方案：

| 形态 | 标识 |
|---|---|
| 悬浮球 | 36px 圆，`linear-gradient(135deg, #DE2910, #DE2910bb)` 底 + 白色线性图标（建议 `ThunderboltOutlined` 或 `CommentOutlined`），带 `box-shadow: inset 0 1px 0 rgba(255,255,255,.28), 0 8px 18px #DE291055` —— **与 `Dashboard` 统计卡的图标块完全同款**，视觉上属于同一套语言 |
| 消息头像 | 28px 圆，同渐变底 + 白色 `L` 字或同图标 |
| 对话内称呼 | 正文以「灵思」自称；不在每条消息前加名字（视觉靠头像区分即可，减少噪音） |
| 产品名出现位置 | ① 抽屉标题「灵思」② 主页 `PageHeader.title = "灵思"` ③ 空态问候「你好，我是灵思。」④ 悬浮球 Tooltip「灵思 · 党务助手」 |

> **图标选择说明**：不建议用机器人图标（`RobotOutlined`）——与党建办公场景的严肃性不搭；`ThunderboltOutlined`（迅捷）或 `CommentOutlined`（对话）更中性。最终以实物预览为准。

## 2. 页面地图（六面）

灵思不做"一个大页面"，而是**六个插入点**，分布在用户已有的工作路径上。这是本设计最核心的判断：**助手出现在工作发生的地方，而不是让用户去助手的地方工作。**

| 编号 | 名称 | 形态 | 位置 | 承载入口 |
|---|---|---|---|---|
| **P1** | 灵思主页 | 独立路由页 `/agent` | 侧栏「灵思」菜单项 | 完整对话、批量任务中心、会话历史 |
| **P2** | 全局悬浮球 + 抽屉 | 悬浮按钮 + 420px Drawer | `MainLayout` 全局 | 快速问答（入口 A 轻量版） |
| **P3** | 就地 Copilot | 内联按钮 + 结果气泡 | 策划书编辑器 / 推文编辑页 / 审核弹窗 | 流程内辅助（入口 B） |
| **P4** | 拟执行清单确认卡 | 卡片（可嵌 P1/P2/P3） | 对话流内 | 批量自动化门禁（入口 C） |
| **P5** | 过程区（流式时间轴 / 折叠条） | 对话流内（AI 消息的过程区） | 对话流内 | 过程透明化（建立信任） |
| **P6** | 受限数据提示块 | 对话流内替换块 | 对话流内 | `restricted` 数据的合规呈现 |

**为什么 P1 与 P2 都要有**：两者不是重复。P2（抽屉）是**顺手一问**——用户正在填表，不想离开当前页；P1（主页）是**专门来干活**——看历史、审任务清单、管理会话。抽屉**不承担**任务中心与会话管理，只保留"最近 10 条会话"的快捷入口（点击跳 P1）。

**贯穿六面的一个共同结构：过程区 / 结论区分置**（§3.5.1）。灵思的每条 AI 消息都由"过程"（思考摘要 + 工具调用，实时可见、事后收起）与"结论"（答复正文 + 卡片）两个区构成。这个分区同时服务三个目标：等待时可感知、完成后不啰嗦、事后可追溯。

### 3.3 左栏：会话列表


| 行为 | 规格 |
|---|---|

### 3.4 空态：提示卡（Prompt Cards）

这是**决定用户会不会用起来**的地方。设计要点：

1. **按权限动态过滤**：`GET /api/agent/tools` 返回当前用户可见工具，前端据此映射成提示卡。干事看不到「起草策划书」卡，避免"点进去被拒"的挫败感。**前 2 张固定（低门槛），后 2 张按权限从高频工具池补足，总数恒为 4**（见 §11.1）。
2. **卡片内容**：一句话问法（用户视角的语言，不是功能名）+ 一行小字说明能产出什么。
3. **点击行为**：填入输入框并**自动聚焦**，**不自动发送**——用户常有微调需求（换活动名、加时间范围），自动发送会导致大量"重发一次"。

```
┌────────────────────────────────┐  ┌────────────────────────────────┐
│ 📋 最近有哪些事等着我处理？      │  │ 📁 找一下第四十期培训班的材料    │
│    汇总待审策划书、稿件与未读通知│  │    按活动 / 类型检索材料库       │
└────────────────────────────────┘  └────────────────────────────────┘
┌────────────────────────────────┐  ┌────────────────────────────────┐
│ 🗓 下周三下午部门开会有空吗？    │  │ ✨ 帮我把这次活动的推文起草了    │
│    查共同空闲时段与排班冲突      │  │    生成草稿，可修改后再提交      │
└────────────────────────────────┘  └────────────────────────────────┘
```

> **文案原则**：主语是"我/你"而非"系统"；每卡只对应一个动作；副文案说产出不说实现。**完整初版文案与动态替换规则见 §11.1。**

| 卡片规格 | 值 |
|---|---|
| 布局 | `display:grid; grid-template-columns: repeat(auto-fit, minmax(260px,1fr)); gap:12px` |
| 卡片 | `--surface-strong` 底，1px `--surface-border`，`--radius-md`，padding 14px 16px |
| hover | `border-color: rgba(222,41,16,.4)` + `translateY(-2px)`（同 `.stat-card`），`transition: .2s var(--easing)` |
| 图标 | 18px，颜色 `var(--color-red)` |
| 主文案 | 14px，`--color-text` |
| 副文案 | 12px，`--color-text-secondary` |

### 3.5 消息流

#### 3.5.1 AI 消息（左对齐）

一条 AI 消息由**两个区**组成，理解这个分区是理解整个对话流的关键：

```
┌─ 过程区（Process Zone）──────────── 进行中展开 / 完成后收为一行 ─┐
│  │ 思考摘要（暗色 + 左虚线）                                    │
│  ✓ ⚡ 查询我的待办        184ms                                │
│  ✗ ⚡ 排班查询            超时                                  │
└─────────────────────────────────────────────────────────────────┘
┌─ 结论区（Outcome Zone）──────────── 一直可见，是消息的主体 ─────┐
│  灵思为你找到 3 份相关材料：                                    │
│                                                                │
│  ┌ [结果卡] 材料 ×3（标题/类型/上传时间/打开）────────────┐   │
│  └─────────────────────────────────────────────────────┘   │
│                                                                │
│  [折叠条] 调用了 3 个工具 · 1 个失败 · 共 1.2s            ▾    │
└─────────────────────────────────────────────────────────────────┘
```

- **过程区**：承载思考摘要与工具调用行（§3.5.3）。**进行中展开、完成后收起**为底部的 P5 折叠条。用户随时可展开回看。
- **结论区**：答复正文 + 结果卡 / 确认卡 / 受限块。这是消息的持久主体，**任何状态下都不折叠**。
- **为什么这样分**：如果把思考与工具行混排进正文，历史消息会充满与当前问题无关的过程噪音——一条两周前的对话打开来先看到五行 `184ms`，这是明显的可用性倒退。分区 + 自动收起让"实时透明"和"事后整洁"同时成立。

- **气泡样式**：`--surface` 底 + 1px `--surface-border` + `--radius-lg`，但**左上角 4px**（`border-top-left-radius: 4px`）以表达"来自助手"，与右下角 4px 的用户气泡形成对话指向。
- **不使用**尾部小三角（会让玻璃质感变脏）。
- **Markdown 渲染**：AI 回复可能含列表/加粗/代码。建议 `react-markdown` + `remark-gfm`，且**必须** `rehype-sanitize`（前端第二道防线）。表格用现有 `GlassTable` 样式覆盖（响应式容器 + `--surface-border`）。
- **复制按钮**：hover 消息时右上角浮现「复制」（`CopyOutlined`），成功 `message.success('已复制')`。
- **重新生成**：仅对**最后一条** AI 消息显示（`ReloadOutlined`）。历史消息重新生成会产生分叉，一期不做。
- **消息级状态行**（放在结论区底部，与折叠条同行右侧）：显示本轮的**模式标识**与**耗时**，如 `规则模式 · 1.2s`。这是 Codex 底部状态栏的轻量对应物——它回答用户必然会有的一个疑问："这是真 AI 答的，还是兜底模板？"。**降级到 `StubProvider` 时必须显式标注「规则模式」**，不能在用户不知情时用模板冒充 LLM 输出（见 §1 铁律③的精神）。

#### 3.5.2 用户消息（右对齐）

- 背景 `var(--color-red)`，文字 `#fff`，`--radius-lg` 但**右下角 4px**。
- 宽度 `min(72%, 560px)`。
- **不做**头像（自己的头像在顶栏已出现，重复）。

#### 3.5.3 思考与工具调用的流式时间轴（本节是本次修订的核心）

**先澄清一个容易混淆的概念**——"流式"在本文里指两件不同的事，必须分开决策：

| 类型 | 内容 | 数据粒度 | 本期是否做 | 理由 |
|---|---|---|---|---|
| **① 事件级增量**（Event Streaming） | 思考状态、工具开始/结束、工具结果摘要、计划生成 | **离散事件**（一次几行 JSON） | **✅ 本期做** | 天然事件模型，与现有 WebSocket 完美契合；是"过程透明"的核心载体，也是 Codex 界面的精髓 |
| **② 字符级增量**（Token Streaming） | 最终答复逐字吐出 | **连续 token** | **二期做** | 需要 `fetch + ReadableStream` 承载，且与"工具调用多轮编排"叠加会让复杂度显著上升（业务设计方案 D7 的判断仍然成立） |

> **修正**：v1.0 的 §3.5.3 把两者笼统归为"一期非流式"，这是不准确的。**一期虽不逐字吐字，但思考与工具调用必须是实时可见的事件流**——否则用户在等待的 3–8 秒里看到的是一个静止的三点动画，无法判断"它在动还是在死"。这块的成本很低（后端本就要产生这些事件，只是多推一次），收益极高。

**设计参照：OpenAI Codex CLI 的 TUI**。Codex 的做法是把一次任务渲染成**一条交错的时间轴**，而不是"用户消息 → 一个 loading → 一条完整回复"。它的关键手法（已核对 `EventProcessorWithHumanOutput` 的渲染实现）：

| Codex 手法 | 具体表现 | 灵思的对应物 |
|---|---|---|
| 思考文本用**暗色（dimmed）**渲染 | 与最终答复的正文明确区分 | 思考块 `--color-text-secondary`，**左侧 2px 虚线竖线**表示"这是过程，不是结论" |
| 每个动作**开始一行、结束一行** | 开始：`exec <cmd>` / `mcp: <server>/<tool>`；结束：`succeeded` (绿) 或 `exited [code]` (红) | 工具行：开始「正在查询活动概况…」，结束「✓ 184ms」 |
| 结束行**带耗时** | 让人判断"它卡在哪儿" | 每个工具行末尾固定显示 `durationMs` |
| 状态用**颜色**区分 | 绿=成功、红=失败、黄=被拒绝 | 复用 `CARD_ACCENT`：`#52A052` / `#DE2910` / `#FA8C16` |
| 「Thinking…」**带已用秒数** | 空转超过 2s 就显示计时 | 「正在思考… 已用 4s」 |
| 拒绝/中断是**一等状态** | 不是错误，是用户的选择 | 任务被取消 → 灰色「已取消」而非红色报错 |

**渲染形态**（一次多轮工具调用的完整时间轴）：

```
[灵思头像] ┌────────────────────────────────────────────────────────┐
          │  ‥ 正在思考…  已用 2s                          ← 计时器，进行中
          │                                                        │
          │  │ 用户问的是"本月活动"，需要先确认当前月份口径，      ← 思考块
          │  │ 再按状态过滤。材料库应该不用查。                   （暗色 + 左侧虚线）
          │                                                        │
          │  ▸ ⚡ 正在查询我的待办…                     ← 工具行(进行中，有脉冲点)
          │  ✓ ⚡ 查询我的待办                          184ms   ← 工具行(完成，绿)
          │  ✓ ⚡ 活动概览查询                          267ms
          │  ✗ ⚡ 排班查询                              超时    ← 失败(红)，不阻断后续
          │                                                        │
          │  ────────────────────────────────────────             ← 分隔线：过程结束
          │  本月共有 3 场活动：                                     ← 最终答复（正文色）
          │                                                        │
          │  ┌ [结果卡] ───────────────────────────────────────┐   │
          │  │ 9/18 主题党日 · 进行中 · 负责人 张老师            │   │
          │  │ 9/25 素拓活动 · 待策划 · 负责人 李老师            │   │
          │  └─────────────────────────────────────────────────┘   │
          │                                                        │
          │  [折叠条] 3 个工具 · 1 个失败 · 共 1.2s          ▾     ← P5，见 §7.1
          └────────────────────────────────────────────────────────┘
```

**五个必须遵守的规则**：

1. **思考块只显示摘要，不显示原始推理链**。后端推送的是"阶段摘要"（如"需要先确认月份口径"），**不是**模型的原始 `reasoning_content`。原因有二：① 原始推理链可能含有被过滤的上下文碎片（数据分级风险）；② 逐字推理对党务场景是噪音，摘要才是有效信息。这一点与 Codex 的 `show_reasoning` 不同——**Codex 面向开发者，灵思面向党务干事，信息密度偏好不同**。

2. **过程区在答复开始后自动降级为 P5 折叠条**。最终答复到达时，上面那一段（思考 + 工具行）**收起为一行摘要**，正文只留答复与卡片。历史消息再次打开时默认就是折叠态。**理由**：过程的价值在于"等待时让人安心"，一旦结论到达，过程就该让位给结论——但它必须**可展开**，这是"事后可追溯"的保证。

3. **工具失败不阻断时间轴**。某一个工具失败（如排班查询超时），时间轴继续走，失败行标红并保留原因（hover 显示）。**不要**把整条消息变成错误态——多工具聚合时，部分失败是常态，整条报错会让用户以为全都没查到。

4. **计时器与动画都必须有 `prefers-reduced-motion` 兜底**。既有 `global.css` 的兜底规则**只覆盖 `.page-transition` 与 `.glass-card`**，新增的脉冲点、计时器动画需自行加同款媒体查询。这是 v1.0 就指出过的坑，在本次新增动画后风险面积变大。

5. **首事件延迟（TTFE）是硬指标，前端必须为它做好承接**（2026-09-13 新增）。指标：**P95 < 800ms**（用户发送 → 收到第一个 `THINKING` 事件）。
   - **后端责任**：`AgentOrchestrator` 进入编排的**第一时间**（意图分类之前）就推 `THINKING`，**不得等首个工具出结果才推**。这是最容易犯的错——把 `THINKING` 当成"第一个工具将要执行"的通知，实际上它应该是"我开始处理了"的通知。
   - **前端责任**：点击发送后**立即**在本地插入一条"占位 AI 消息"并显示「正在思考…」，**不等首个事件到达才渲染气泡**。否则即便后端 300ms 就推了事件，用户看到的仍是 300ms 的空白。
   - **为什么要立这条指标**：改流式之后，用户的体感时钟从"发出去 → 答复出现"变成了"发出去 → **第一个事件**出现"。如果 TTFE 是 1.5s，即便总时长 2.8s 达标，用户依然觉得"点了没反应"——**流式等于白做**。一个指标盖两件事，会让这种退化被掩盖。

**传输通道与事件契约**：

| 项 | 取值 | 说明 |
|---|---|---|
| 通道 | **复用现有 STOMP WebSocket**，新增 `/user/queue/agent/stream`（一期） | 若无法在对话请求期间建立用户定向订阅，则**降级方案**为 `POST /api/agent/chat` 返回 `streamId` + 前端轮询 `GET /api/agent/streams/{streamId}`（500ms，事件带 `seq`，断点续读）。两种通道对前端是**同一个 `AgentStreamEvent` 契约**，切换不改 UI 代码 |
| 事件体 | `AgentStreamEvent { streamId, seq, type, payload, ts }` | `seq` 单调递增；前端按 `seq` 去重排序，乱序到达不错位 |
| 事件类型 | **一期实发**：`THINKING` / `TOOL_START` / `TOOL_END` / `PLAN_READY` / `MESSAGE_DONE` / `ERROR`；**二期预留**：`MESSAGE_DELTA` | 一期只发到 `MESSAGE_DONE`（一次性完整答复）；`MESSAGE_DELTA` 现在不出现在实现里，但**写进契约**，二期只需后端多发一类事件 + 前端加一个 `case` |
| 兜底 | 若 5s 内未收到任何事件 → 显示三点跳动（v1.0 的原方案作为兜底保留） | 老浏览器 / WebSocket 断连时不能白屏 |

> **为什么 `MESSAGE_DELTA` 现在就在契约里预留**：这样二期开流式是**后端多发一类事件**，前端只需在处理函数里加一个 `case`。契约先行，避免二期要做破坏性改动。这与 D11"把变更压到编译期暴露"是同一思路。

**是否需要改业务设计方案的 D7？** 需要，但只是**澄清而非推翻**。D7 原文"一期先做非流式"应修订为"**一期做事件级流式（Tool/Thinking），不做字符级流式**"。这是对 D7 结论的收窄，不是反转——D7 关于"不引入 MQ/Redis""复用 WebSocket""为什么不用 EventSource"的判断全部继续成立。

| 状态 | 表现 |
|---|---|
| 请求已发出、未收到首个事件 | 三点跳动占位（3 个 6px 圆点，`animation: bounce 1.2s infinite`，错开 0.15s）+ 「正在思考…」 |
| 收到 `THINKING` / `TOOL_START` | 切换到时间轴形态（见上图），显示计时器 |
| 请求超时（> 30s，与 `http.ts` timeout 一致） | 时间轴原地转为「请求超时」+「重试」按钮，**已收到的工具行保留**（不要清空，那是有效信息） |
| 用户中止（发送按钮变「停止」） | 时间轴尾部追加灰色「已中止」行，**已执行的工具行保留**；若工具已有副作用则提示「已执行的查询不会撤销」 |
| WebSocket 不可用 | 降级为 3s 轮询 + 三点跳动（无实时时间轴） |

```
┌────────────────────────────────────────────────────────────┐
│  问点什么…                                                  │
│                                                            │
│                                       [🧩 功能] [ ➤ 发送 ] │
└────────────────────────────────────────────────────────────┘
灵思的回答基于你的权限范围；越权内容会说明原因，不会静默省略。
```

| 交互 | 规格 |
|---|---|
| 发送键 | `Enter` 发送；`Shift+Enter` 换行（中文用户习惯；不做 Enter 换行） |
| 空内容 | 发送按钮 disabled |
| 发送中 | 输入框保持可编辑（可预打下一条），发送按钮变为「停止」。**「停止」的真实语义**：① 前端停止接收后续事件并保留已收到的时间轴；② 调 `POST /api/agent/chat/{streamId}/abort` 通知后端停止编排。**不发 abort 就是"只是不看"，服务端可能仍在跑工具并产生副作用**——这是必须区分的，因此按钮 Tooltip 写「停止本次回答」，并在中止后于时间轴尾部标注「已中止」+（若有副作用）「已执行的查询不会撤销」 |
| 发送中的二次发送 | 允许（进入 **队列**）：用户可在上一条未完成时继续输入并提交，第二条排在后面顺序执行。**不做并行**——多轮工具调用并行会让"哪条消息对应哪次工具调用"彻底混乱 |
| 功能菜单 `🧩` | `Dropdown`，列出**当前用户可见工具**按类别分组（查询 / 起草 / 批量）。点击后**在输入框前缀插入一个可删除的 chip**（如 `[材料检索]`），约束本次为定向调用。这是"提示卡"以外的第二条引导路径 |
| 底部提示 | 12px secondary，**必须有**——它是"AI 可能答错"的必要免责，也是 D3 权限口径的用户侧表达 |
| 草稿保留 | 输入内容按 `conversationId` 存 `sessionStorage`，切换会话/刷新不丢 |

## 4. P4 拟执行清单确认卡（最关键的一个组件）

这是铁律②（写操作先出拟执行清单）的用户侧载体，也是**整个灵思里风险最高的界面**——用户在这里点一下，数据就变了。

### 4.1 视觉原型来源

`ActivityCreditModal` 的第 5 步（`components/credit/ActivityCreditModal.tsx` L375-387）已经被验证过：

```tsx
<div style={{ textAlign: 'center', padding: '24px 0' }}>
  <div style={{ fontSize: 28, fontWeight: 600, color: 'var(--color-primary)' }}>
    将为 {totalSelected} 人各加 {credit ?? 0} 分
  </div>
  <div style={{ marginTop: 8, color: 'var(--color-text-secondary)' }}>
    共计 {totalCredit} 分 · 每人一条加分记录，可整体撤回
  </div>
  ...
</div>
```

灵思的确认卡继承这个"**先给数字，再给解释**"的视觉层级，但需要补三件模态弹窗不需要的东西：**明细可展开、跳过原因必现、不可逆提示**。


### 4.3 设计规则（逐条给理由）

| 规则 | 规格 | 理由 |
|---|---|---|
| **双数字并置** | 「将执行 N」为主要数字（28px，`--color-red`）、「将跳过 M」为次要（20px，`#FA8C16` 若 M>0 否则不显示） | 只报成功数是最容易骗人的做法。M>0 时**必须**与 N 同屏，且**不能被折叠隐藏**（数字在外面，明细才可折叠） |
| **跳过原因不进折叠** | 折叠头（summary 行）本身就写「查看被跳过的 1 人（需处理）」 | 用户看到"1 人将被跳过"会想问"为什么"，折叠头直接给出入口 |
| **跳过项默认展开** | 若 `skipped.length <= 3`，默认展开 | 少量跳过项往往是**错误信号**（同名冲突、学号缺失），默认展开能提高用户处理的概率 |
| **不可逆提示分级** | 可撤回 → `⚠️` 橙色文案「可通过任务记录整体撤回」；不可撤回 → `🚫` 红色文案「此操作不可撤销，请确认无误」（文案更硬） | 不同工具风险不同，模板化提示会让人麻木 |
| **危险按钮不做主按钮** | 「确认执行」用 `type="primary"`（红底）。**但**若该任务不可撤回，主按钮前缀加 `WarningOutlined` | 保持主按钮视觉一致，靠图标传达风险增量 |
| **确认按钮的二次确认** | **不弹二次确认弹窗**（重要） | 清单卡本身就是二次确认。再弹一层会让用户形成"无脑点确认"的肌肉记忆，反而降低安全性 |
| **一次性令牌** | 卡片在 `PENDING_CONFIRM` 时携带 `confirmToken`；点击后立即置灰 + loading，**失败不做自动重试** | 幂等由后端乐观锁保证；前端不重试是避免"到底成没成"的歧义 |
| **已执行态** | 卡片原地变为结果卡（不消失）：`✅ 已执行 · 42 成功 / 0 失败` + `[查看结果]` + （可撤回时）`[撤回本次]` | 用户的注意力停留在原处，不需要"去别的地方找结果"。**卡片消失是最差的设计** |
| **扫描态** | `RUNNING` 时进度用骨架 + 文案「正在执行 42 条…」；超过 5s 提示「执行时间较长，可以去做别的事，完成后会通知你」（配合 WebSocket 推送） | 长任务必须给"可以离开"的许可，否则用户死盯屏幕 |

### 4.4 明细列表规格

| 项 | 规格 |
|---|---|
| 行高 | 32px，`border-bottom: 1px solid var(--surface-border)`（末行不画） |
| 列 | 主标识（姓名/标题）+ 副标识（学号/编号，12px secondary）+ 状态/原因 |
| 最大高度 | 280px，超出内部滚动（`overflow:auto`） |
| 大数据量 | `> 100` 条时**不渲染全部**；显示前 100 条 + 「查看全部 1000 条」（点击后跳任务详情页分页） |
| 虚拟滚动 | 一期不做（项目无虚拟列表依赖）；靠"限制 100 条"控制 |

### 4.5 通用性：一套组件服务所有写类工具

`AgentActionCard` 的 props 必须**只依赖后端的 `plan` 结构**，不感知具体业务：

```ts
interface AgentPlan {
  planId: number
  summary: string           // "第四十期培训班 · 素拓批量加分"
  total: number
  items?: PlanItem[]        // 明细（可能为空，如"发布公告"）
  skipped?: { label: string; sub?: string; reason: string }[]
  detailLines?: string[]    // 补充说明（如"来源：签到名单第一组/第二组"）
  reversible: boolean
  confirmToken: string
}
```

各业务的差异全部通过 `summary` / `detailLines` / `items[].label` 的**文案**表达，组件本身零分支。这样新增一个写类工具，前端**零改动**——这是 §7 解耦契约在前端的对应物。

### 5.4 `useWebSocket` 扩展

现有 `useWebSocket` 只处理 `/user/queue/notifications`（`hooks/useWebSocket.ts` L25-50）。灵思需要**两条**新订阅：

```ts
// ① 长任务完成推送（一期 F0 就要）
client.subscribe('/user/queue/agent', (msg) => {
  const data = JSON.parse(msg.body)
  if (data.type === 'AGENT_TASK_DONE') {
    useAgentStore.getState().applyTaskResult(data)   // 更新任务状态 + 追加结果卡
    notification.success({ message: '灵思任务已完成', description: data.summary })
  }
})

// ② 对话过程事件流（一期 F1 起，驱动 §3.5.3 的时间轴）
client.subscribe('/user/queue/agent/stream', (msg) => {
  const evt: AgentStreamEvent = JSON.parse(msg.body)
  useAgentStore.getState().applyStreamEvent(evt)     // 按 seq 去重、增量更新过程区
})
```

**改造建议**：现有 `useWebSocket` 是一个 `useEffect` 内联全部逻辑，订阅硬编码。建议**抽出订阅注册表**（`const SUBSCRIPTIONS = [{ topic, handler }]`），使新增队列不改动核心逻辑。这是本次唯一建议重构的既有文件，改动量约 30 行。

> **断连处理**：现有实现没有重连后的"补拉"逻辑。灵思的过程区依赖 `seq`，若断连期间丢事件会导致时间轴缺行。约定：`onConnect` 回调中除订阅外，**额外拉一次 `GET /api/agent/streams/{streamId}?since={lastSeq}`** 补齐缺口。这是既有代码没有的能力，属于必要新增（不改动现有的通知订阅行为）。

## 6. P3 就地 Copilot

### 6.1 出现位置（一期 3 处）

| 位置 | 触发 | 产出 | 权限 |
|---|---|---|---|
| 策划书编辑器（空章节） | 章节正文为空时，章节右上角出现「✨ 起草本章」 | 生成段落，**预览后**填入 `contenteditable` | `activity:edit` |
| 推文编辑页（新建时） | 选好关联活动后，标题输入框下方出现「✨ 根据活动生成初稿」 | 标题 + 摘要 + 正文，**整体预览**后填表 | `LEADER` 等价 |
| 审核弹窗 | 打开时，审核意见框右上角出现「✨ 参考意见」 | 按完整性/预算/时间冲突预填意见文本 | `activity:review` |

### 6.2 交互（以策划书章节为例）

```
┌─ 二、活动主题 ──────────────────────────  [✨ 起草本章] ─┐
│                                                        │
│  （空，点击输入…）                                      │
└────────────────────────────────────────────────────────┘
                    ↓ 点击后
┌─ Popover (width 460) ──────────────────────────────────┐
│  正在根据活动信息起草…                                   │
│  ─────────────────────────────────────────────────    │
│  以"学思践悟二十大精神"为主题，围绕…                      │  ← 生成结果，可滚动
│  ─────────────────────────────────────────────────    │
│  [ 重新生成 ]  [ 取消 ]                    [ 采纳并填入 ]│
└────────────────────────────────────────────────────────┘
```

| 决策 | 取值 | 理由 |
|---|---|---|
| 载体 | antd `Popover`（`placement="bottomRight"`），**不用 Modal** | 要能看到被编辑的原段落做对照；Modal 会遮住上下文 |
| **不流式** | 一期一次性返回，显示「正在起草…」 | 与 D7 一致 |
| 采纳行为 | 填入内容后**光标定位到末尾**，进入可编辑状态 | 用户的下一步必然是修改，不是阅读 |
| 重新生成 | 携带一个隐式 `seed`（时间戳），保证结果不同 | 同参数重复生成会得到相同结果，用户会以为"坏了" |
| 结果长度 | 若生成 > 400 字，`Popover` 内滚动（max-height 260px） | 防止气泡超出视口 |
| 失败态 | 「起草失败：{原因}」+ [重试]。**不自动降级到 Stub 并写入** | 写库内容必须是用户看过的东西；静默降级会让用户把模板文案当成 AI 输出 |

### 6.3 结果回填的边界（重要）

- Copilot **只往表单/编辑器里写字**，不替代用户提交。
- **不自动提交审核**（铁律②的延伸）：策划书章节写完仍是 `DRAFT`；推文生成后仍需用户点「提交审核」。
- 回填**不覆盖**已有内容：仅在目标为空时出现按钮；目标非空时按钮**移到工具栏**并提示「将替换现有内容」（需用户主动点击，不主动打扰）。

## 7. P5 过程区（流式时间轴 & 折叠条）与 P6 受限数据块

### 7.1 P5：过程区 —— 实时是时间轴，事后是折叠条

P5 有**两种形态**，是同一个组件的两个状态，**不是两个组件**：

**形态 A：进行中的时间轴**（`RUNNING`，实时推送驱动，见 §3.5.3）

```
  ‥ 正在思考…  已用 2s
  │ 需要先确认月份口径，再按状态过滤。
  ✓ ⚡ 查询我的待办                          184ms
  ▸ ⚡ 活动概览查询…                     ← 进行中：脉冲点 + 省略号
  ✗ ⚡ 排班查询                              超时
```

**形态 B：完成后的折叠条**（`DONE`，默认收起）

```
[⚡] 3 个工具 · 1 个失败 · 共 1.2s                              [展开 ▾]
```

展开后（形态 B 展开 = 形态 A 的定格，**行内容完全一致**）：

```
  │ 需要先确认月份口径，再按状态过滤。
  ✓ ⚡ 查询我的待办          查询我的待办        184ms   ✓
  ✓ ⚡ 活动概览查询          活动概览            267ms   ✓
  ✗ ⚡ 排班查询              排班查询            超时    ✗ 连接超时，可重试
  ⚠️ 其中 1 个工具未返回结果，答复可能不完整
```

| 规格 | 值 |
|---|---|
| 位置 | AI 消息的**过程区**（结论区之上）。折叠条形态时固定在结论区**最下方**（结果卡之后） |
| 默认 | **进行中：展开**（让用户看到"它在动"）/ **完成后：折叠**（历史消息） |
| 字号 | 过程区正文 12px；思考块 12px `--color-text-secondary`；工具行 12px |
| 思考块样式 | `--color-text-secondary` + `border-left: 2px dashed var(--surface-border)` + `padding-left: 10px`；**不用斜体**（中文斜体渲染差） |
| 工具行图标 | 进行中 `◌`（脉冲动画）；成功 `✓`（`#52A052`）；失败 `✗`（`#DE2910`）；跳过 `–`（`#8C8C8C`） |
| 工具名显示 | **显示中文业务名，不显示工具标识符**。`queryMyPendingWork` 对用户无意义。中文名由前端按 `tool` 字段映射（`toolLabels.ts`，与后端工具清单一一对应） |
| 耗时 | 每个已完成工具**必须显示** `durationMs`；总耗时显示在折叠条上。**这是"卡在哪"的唯一线索**，Codex 的做法值得直接照搬 |
| 进行中的工具行 | 文案用「正在……」（如「正在查询活动概况…」）+ 脉冲点；**不显示虚假进度百分比**（无法预估） |
| 失败工具 | 行内标红 + 原因（hover 或行内小字）；**折叠态也必须在摘要里报出数量**（「其中 1 个失败」）——失败被折叠隐藏是最坏的组合 |
| 未识别工具名 | 回退显示原始 `toolName`（容错，避免新增工具时前端显示空白） |
| 历史回看 | 从 `agent_tool_call` 表读回（后端持久化了 `tool_name / duration_ms / result_status`），**因此过程区是真实历史而非前端临时状态**——刷新页面后仍可展开回看 |

> **为什么要显示**：铁律①③的信任基础是"我知道它查了什么"。不透明会让用户疑心"它是不是看了不该看的"。
> 更重要的是一份 HCI 研究的结论：当 Agent 的行为不可见时，用户必须先**在脑中重建它做了什么**，才能判断结果是否可信——这一步重建成本极高，且经常失败（用户要么盲信，要么全不信）。**因此过程区不是装饰，它是"让用户能验证"的前提**。这也是最便宜的可解释性实现：后端本就要产生这些事件，前端多渲染一列而已。
>
> **与 Codex 的差异（有意为之）**：Codex 把推理原文用暗色全量吐出，因为它面向开发者、鼓励审阅推理；灵思只显示**阶段摘要**（"需要先确认月份口径"），因为党务干事要的是"它在查什么"，不是"它在怎么想"。**照搬 Codex 的推理全量输出会是错的**——这里是"参考其呈现结构，不照抄其信息密度"。

### 7.2 P6：受限数据块

当工具返回 `restricted` 数据（如函调家系信息），LLM 上下文里根本没有内容，AI 只能给固定话术 + 深链：

```
┌─────────────────────────────────────────────────────┐
│ 🔒  该信息受权限保护，无法在此展示                     │
│                                                     │
│     函调家系信息属于受限数据，仅可在党务台账页面查看。  │
│                                    [前往查看 →]      │
└─────────────────────────────────────────────────────┘
```

- 底：`--surface-strong`；左边框 3px `#FA8C16`（警示非错误）。
- **不用红色**——这不是错误，是设计行为，用红会让用户以为系统坏了。
- 「前往查看」深链由后端 `references[]` 给出（如 `/party/members/{id}`），前端只负责渲染跳转，**不自行拼路径**。
- 同理用于 `sensitive` 数据被脱敏后的残段：显示脱敏值（`张*`）并在块底标注「已按权限脱敏」。

### 11.1 决策 2 详述：提示卡文案（建议初版，可用性优先）

原则：**用用户会说出口的话，不用功能名**。三条判据——
1. 主语是"我/你"而不是"系统"（"有哪些待我审核" ✓；"策划书审核查询" ✗）
2. 每张卡**只对应一个动作**，不合并（合并后 LLM 意图识别会摇摆）
3. 副文案说清**产出什么**，不描述怎么实现

| # | 卡片主文案（用户问法） | 副文案（产出说明） | 归属 |
|---|---|---|---|
| 1 | 最近有哪些事等着我处理？ | 汇总待审策划书、待审稿件与未读通知 | `queryMyPendingWork` |
| 2 | 找一下第四十期培训班的材料 | 按活动 / 类型检索材料库 | `searchMaterials` |
| 3 | 下周三下午部门开会有空吗？ | 查共同空闲时段与排班冲突 | `queryCommonFreeTime` |
| 4 | 帮我把这次活动的推文起草了 | 生成草稿，可修改后再提交 | `draftArticleFromActivity` |

**为什么第 1 张卡是"等我处理"而不是"查活动"**：这是**最高频且最痛**的场景（用户打开系统往往就是想看"有没有事要做"）。把它放第一张，等于给了一个"每天都会点"的理由，比任何功能介绍都有效。

**动态替换规则**：卡片不是固定 4 张，而是**从 `GET /api/agent/tools` 反查**——前 2 张固定（`queryMyPendingWork` + `searchMaterials`，权限门槛低），后 2 张按用户权限从"高频工具池"里补足（低权限用户看到 `queryNotifications` / `querySchedule`；有 `activity:edit` 的用户看到起草类）。**总数为 4，不增不减**（超过 6 张会变选择困难，少于 3 张显得能力单薄）。

### 11.2 决策 5 详述：头像图标（建议 `ThunderboltOutlined`）

| 候选 | 语义 | 问题 |
|---|---|---|
| **`ThunderboltOutlined`（闪电）** ← 建议 | "迅捷、一说就办" | 无 |
| `CommentOutlined`（对话框） | 直白表达"对话" | 太通用，和 antd 的注释/评论语义混淆；且"对话"不是产品价值，**"帮你把事办了"才是** |
| `RobotOutlined`（机器人） | 直白表达"AI" | **明确排除**：与党建办公场景的严肃性不搭，且"机器人"暗示"不可靠/玩物" |
| `BulbOutlined`（灯泡） | "灵光一闪"，呼应"灵思" | 可作备选；但灯泡在 UI 中常表示"提示/tip"，易被误读为帮助按钮 |

**为什么选闪电**：① 它是 `Dashboard` 统计卡已在用的视觉语言（图标块同款渐变），**选它等于让侧栏、悬浮球、统计卡三处的图标语义连贯**；② "迅捷"是对用户最核心的承诺（Agent 的价值就是省事）；③ 不预设"AI"概念——党务干事不关心是不是 AI，只关心"好不好用"。

> **实现建议**：先用 `ThunderboltOutlined`（零成本，马上能看），**F4 时若有设计资源再换自定义 SVG**——换的成本只是 `AgentAvatar.tsx` 一个文件。**不要为这个图标阻塞开发。**

**复核中确认的关键事实（供后续参考）**：现有推送 payload 是**刻意做薄的**——`Map.of("type", "NEW_NOTIFICATION", "unreadCount", unread)`，源码注释写明"payload 仅包含类型和未读计数，前端收到后调 REST API 刷新"。**灵思的过程事件流与此不同**：它必须把 `THINKING` / `TOOL_END` 的实际内容推过去（否则前端无从渲染时间轴），因此**不能照搬"只推信号、内容靠 REST 拉"的既有约定**。这是两套 payload 策略的有意差异，需在实现时明确区分，避免实现者按惯性把事件也做成"只推类型"。
