## 1. 业务目标

管理员登录后，在当前组织的“组织设置 → 角色与权限”中完成：

- 从空白、系统模板或本组织已有角色创建新角色。
- 修改角色名称、说明、操作权限及每项操作的数据范围。
- 查看角色下用户，分配、替换单用户角色；先处理引用，再停用角色。
- 查看用户主角色、有效业务权限及治理能力来源摘要。
- 查询角色修改记录和发布快照。

后续增强：多种受限管理员配置、批量分配/停用迁移、具体对象权限诊断、历史版本恢复界面。下文相关章节保留目标设计，但不作为首版必须完成的功能；管理端停用首版只开放“无有效引用”路径。

管理员直接在管理端完成授权配置。新增角色不需要开发，也不需要逐次请求平台运维。所有操作限定当前组织；角色名称、模板与职务不决定管理员资格。

本期仍采用一个账号一个业务主角色。管理员身份是附加的组织治理授权；它不占用主角色，也不引入两个业务角色的权限叠加。

单主角色是首版取舍，兼任职责需要组合成一个角色；对每人复制例外角色会增加维护成本。首版不承诺解决多节点任职和复杂兼任，应通过实际使用情况再决定是否引入多角色模型。

## 2. 管理员账号如何确定

### 2.1 身份与权限来源

注册组织的账号成为组织所有者，默认可进入角色权限管理。所有者可为本组织其他有效账号授予管理身份，设置其管理能力、可管理对象、可授权内容和期限。

```text
账号
├─ 业务主角色：例如文秘干事 → 决定业务访问和数据范围
└─ 管理身份：例如角色管理员 → 决定可以维护哪些角色和授权
```

`TEACHER`、`DIRECTOR` 等业务角色不自动等于管理员。迁移存量组织时，将确认需要保留的管理权转为显式委派，并由有效所有者接管；不能只靠角色级别推断。

目录由发布流程固定分类为 `BUSINESS / ORG_GOVERNANCE / PLATFORM`。`role_permission` 只存业务授权；`user:view/manage/reset-password`、`role:*`、组织配置/架构/邀请/审计能力存所有者关系或委派的 `management_capabilities`，不允许通过普通角色授予。平台能力来自独立平台身份。

服务端分别解析 `businessPermissions` 和 `managementCapabilities`。为了沿用现有 `hasAuthority` 可以投影有效权限码，但治理接口还必须验证有效委派、目标边界和受保护身份，不能只检查投影码；`me` 分别返回来源，客户端不参与判定。业务角色失效不自动撤销治理身份，治理恢复入口独立检查账号、组织和有效委派；业务访问仍拒绝失效角色。

### 2.2 提供三种管理配置起点

下表为所有者设置管理身份时的预设组合，实际以保存的显式能力和边界为准；修改预设不自动改变既有管理员。

首版只实现“组织管理员”：管理对象固定为全组织普通对象，仍以显式业务权限及范围清单限制可授予内容。角色管理员、账号管理员、节点边界和角色白名单编辑器是后续增强，不能在首版显示为已可用。

| 配置起点 | 默认提供 | 默认不提供 |
| --- | --- | --- |
| 组织管理员 | 管理角色与普通账号、调整授权、分配角色、查看治理记录；默认管理全组织普通对象 | 增删其他管理员、所有者交接、平台管理、自动读取业务敏感内容 |
| 角色管理员 | 查看、新建、编辑和发布获委派的普通业务角色及其授权 | 默认不替用户更换角色、不重置账号密码、不管理其他管理员 |
| 账号管理员 | 查看范围内账号、分配白名单角色、邀请及停用普通账号 | 修改角色授权、扩大可分配角色名单；密码重置需另勾选 |

三种预设共用委派模型，不另加 `isAdmin` 布尔字段。所有者可以在预设基础上调整能力，例如给角色管理员增加角色分配权。普通角色权限页不能授予这些治理能力。

### 2.3 所有者设置管理员的流程

入口：“用户与邀请 → 用户详情 → 管理身份”，仅所有者可编辑。

1. 选定同组织有效账号，首版选择组织管理员；其他配置起点后续开放。
2. 确定管理能力：查看角色、维护角色、调整授权、分配角色、管理账号、查看审计等。
3. 首版管理对象为全组织普通对象，允许创建和维护普通业务角色；后续才开放节点子树、角色维护/分配白名单。
4. 设置可授权清单：操作权限及允许的范围类型；敏感字段权限单独明确勾选。
5. 设置期限，预览后保存。管理身份变更立即更新授权版本。

可授权清单保存为明确的权限码和范围规则，不保存“所有未来权限”通配符。组织新启用领域包、新发布权限点后，需要所有者扩充管理员授权清单。

账号的业务主角色改动不自动撤销或扩大管理身份。停用账号会阻止两类能力；撤销管理身份只撤销管理能力，保留原业务角色。所有者本人不能通过该入口被撤销，交接按总方案独立处理。

可授权领域权限清单绑定组织当前 `pack_activation_version`；领域包停用再启用后，旧清单须由所有者重新确认，不因原先勾选过就自动恢复。

### 2.4 可授权上限与自我提权

管理员可向角色授予的业务权限，必须同时满足：应用已实现、组织能力可用、所有者已委派该操作及范围。**不要求管理员本人先拥有该业务权限。**

例如，所有者允许角色管理员配置 `party:view`，角色管理员可以给“党务档案员”添加此权限；他自己的业务主角色没有该权限时，仍不能读取党务台账。只有业务主角色的显式授权才决定其业务访问。

管理员不能修改自己的业务角色分配，也不能通过扩大自己正在使用角色的授权获得额外能力；如果确有需要，由所有者在明确展示影响的专用操作中处理。普通管理员不能更换所有者或其他有管理身份账号的主角色、重置其密码、停用或删除他们；涉及这些账号的共享业务角色变更也需所有者处理。

这里是职责分工，不是对恶意授权管理员的强保密承诺。兼有建号、授角或凭证控制能力的人可能通过另一个账号取得其可授予的权限，禁止直接修改自身不能消除这条路径。首版按所有者信任委派处理：无代登录，新账号由本人设置密码，密码重置只向目标本人交付设置链接，不向操作者显示凭证；敏感可授权清单需所有者明确选择。若业务要求防范恶意管理员，需另立身份核验、职责分离或多人审批方案。

## 3. 管理端页面结构

### 3.1 角色列表

页面固定显示当前组织名称，提供新建、搜索、状态筛选和来源筛选。列表字段：角色名称、说明、来源、状态、操作权限数量、使用人数、最后修改人和时间。

“来源”分为空白创建、模板创建、角色复制；来源仅说明配置起点。列表由服务端返回当前管理员可见角色，前端不再枚举 7 个固定角色码。名称可改，稳定 ID 与系统生成编码不随名称变化。

| 角色状态 | 可进行的操作 |
| --- | --- |
| 草稿 | 编辑、配置待发布权限、复制、删除；不可分配给用户 |
| 启用 | 调整权限、维护说明、分配人员、停用；修改中的表单不影响已生效配置 |
| 停用 | 查看、保存工作稿、复制、预览后重新启用或归档；不可新分配 |
| 归档 | 仅查看历史和复制；不再编辑或启用，角色 ID 与编码保留 |

角色名称在组织内唯一，比较时去除首尾空格并按统一规范检查；编码在组织内永久唯一。只允许删除从未启用且无历史引用的草稿，其他角色通过停用、归档保留审计。新增 `ARCHIVED` 角色状态是对总方案生命周期的补充。

### 3.2 角色详情

采用“基本信息 / 权限配置 / 使用用户 / 变更记录”四个页签。详情顶部展示状态、来源和版本；后端给出允许操作及不可操作原因。

```text
组织设置 / 角色与权限 / 活动协调员                 复制角色  更多
状态：启用    使用用户：12 人    最后修改：李某

基本信息 | 权限配置 | 使用用户 | 变更记录
┌ 模块与搜索 ───────┬ 操作权限 ────────────────────────────┐
│ 活动管理          │ 权限             允许    数据范围     │
│ 排班考勤          │ 查看活动         已选    全组织       │
│ 成员与档案        │ 编辑活动及任务   已选    本节点及下级 │
│ 内容宣传          │ 审核策划         未选    —            │
│ …                 │ [仅看已选] [仅看改动]                 │
└───────────────────┴─────────────────────────────────────┘
已修改 3 项，预计影响 12 人                   取消修改  预览并保存
```

界面展示中文名称与简短说明，权限码放在详情提示中。主列表使用常见操作名称“查看、创建、编辑、删除、审核、发布、导出”，避免要求管理员理解后端实现。

现有 `activity:assign` 的种子名称是“分配部门”；任务写接口及生成任务工具实际依赖 `activity:edit`。首版沿用真实粒度，不能把它显示成“仅能分配任务”。若以后拆出任务权限，应同步修改 API、Service、工具和迁移，未完成前不提供该独立选项。

### 3.3 权限编辑器规则

- 逐项开关操作；启用操作后设置它支持的数据范围，关闭后该范围不再参与授权。
- 模块标题只表示分组，不作为可持久化权限。“选择本页可授权操作”只选择当前加载、可见且可授权的项，不能隐式包含隐藏项或后续新增权限。
- 新选操作必须显式选择范围；从模板复制时显示继承来的默认范围，不能静默使用 `ORG`。
- 操作依赖缺失时，提示“编辑成员还需查看成员”，展示拟补充项并让管理员确认；不静默增加权限。
- 范围也检查依赖：需要对应查看权限的编辑、审核或导出操作，其作用范围须被查看范围覆盖；不能保存“只看本人，却能编辑全组织”的配置。
- 未启用领域包单独显示不可用说明；管理员授权上限外的操作显示受限原因，不允许构造请求绕过。
- 用户修改获委派角色时，超出其上限的现有授权显示只读摘要。保存会保留该部分，不允许把不可编辑权限因界面未展示而清空。对这些权限的修改需要所有者处理。
- 预览展示完整有效配置。服务器读取当前配置，将管理员允许变更的差量合并后再校验；省略无权编辑项时保留原值，显式请求修改或删除该项时拒绝并说明原因，不能静默忽略越权请求。
- 原有只读授权可保留不代表原样重授。新增、修改和明确撤销只检查本次差量的编辑上限，再检查合并配置的依赖与受影响对象；分配角色则检查整个角色全部有效权限。不能用“全角色超上限”阻止所有合法局部编辑，也不能让局部编辑权变成完整分配权。
- 领域包关闭或授权版本过期的项显示“待重新确认”，保留旧配置但不计入有效权限；普通保存不能顺带恢复它。明确重新勾选并发布后才写入当前领域包版本。
- “本节点及下级”按最终使用该角色的用户主节点解释，不按当前管理员节点解释。
- 数据范围依赖可用字段：活动需完成主办节点映射，任务 SELF 需明确账号关联；尚未具备的范围禁选。活动主办文字、负责人姓名不能作为身份匹配依据，迁移规则见总方案 §5.3.1。
- 页内切换、离开和刷新前提示尚未保存的修改；保存失败保留表单，禁止提示成功后再异步写入。

### 3.4 有效权限查询

首版提供权限及来源摘要；以下具体对象诊断为后续增强。

入口：“用户详情 → 有效权限”。有 `user:view` 且在管理对象范围内的管理员，按模块查看该账号的业务权限、数据范围、来源角色、组织领域包状态及最近授权变更。

查询某项操作返回“允许 / 不允许 / 仅限范围内”，并解释权限未授予、领域包停用、角色失效或数据范围限制等原因。可在管理范围内选具体业务对象验证，例如“是否能编辑活动 A”；服务器只接受真实同租户对象并按目标用户身份计算，不允许任意查询其他组织 ID。

诊断只返回结论、范围及规则来源，不返回对象敏感正文，也不签发用户令牌或代登录。治理能力单独列出来源委派，不能混入主角色权限造成误解。

## 4. 管理员的关键操作流程

### 4.1 新建并启用角色

新建 → 选空白/模板/本组织角色 → 填名称说明 → 保存草稿或配置权限 → 服务端校验并预览 → 保存并启用 → 进入使用用户页。

角色 ID 在草稿保存时生成，重复提交带幂等键避免重建。新建权限草稿与生效授权分开；角色维护权允许保存草稿，只有获得授权调整权的管理员才能发布。草稿可包含拟议权限，保存不代表有权发布，预览和应用均按当前上限检查。创建者不会自动成为该角色的使用者。

复制默认复制权限与范围，不复制使用用户、岗位绑定、邀请、管理身份和历史记录。不能复制其他组织角色。包含自己不可授予权限的复制来源，先展示受限项，由用户确认以可授权子集创建新角色，不能悄悄删除后宣称完整复制。

### 4.2 修改已启用角色的权限

打开现有配置 → 修改操作或范围 → 点击“预览并保存” → 服务端生成变更清单 → 管理员确认该清单并提交 → 事务更新授权与版本 → 通知受影响用户刷新权限。

预览至少包含角色及组织、操作者、增加/撤销的权限、范围扩大/缩小、实际影响人数、管理范围内可见人员、将失效的邀请和待确认任务数量。未被修改的权限保留，全部可编辑权限取消时明确展示“角色将没有可编辑业务权限”。

邀请和待确认任务数量仅在各自确有完整判定规则时展示，否则标注“需执行时复核”，不伪造精确影响数。角色配置编辑可先保存服务端工作稿；用户明确发布前，原已发布版本继续生效。

普通保存使用一次预览确认，不要求额外审批。撤销权限、增加敏感字段读取、扩大范围及清空配置使用同一预览页突出变化，不再叠加多层确认弹窗。

提交时再次验证管理身份、上限、角色版本、影响人员及组织状态。预览期间发生调岗、角色分配、委派撤销或授权变化时拒绝旧预览，返回差异并让管理员刷新预览；不能让预览成为可无限重放的授权凭证。

### 4.3 分配或替换用户角色

有两条入口：“用户详情 → 调整角色”以及“角色详情 → 使用用户 → 添加用户”。两条路径调用同一分配服务，均明确这是替换原主角色。

管理员选择范围内普通账号 → 选可分配角色 → 对比旧/新权限及范围 → 预览 → 应用。默认不改变部门和职务；如果同时调岗，需要将角色与节点作为同一个拟变更一起检查，不按旧节点验证后再写新节点。

候选用户与角色由服务端过滤。管理员只可维护自己管理节点内的普通账号；角色的所有有效权限必须落在其分配上限内。允许维护角色中的部分权限不代表允许把整个高权限角色分配出去。

首版只处理单账号替换。后续批量增强建议每次最多 100 个账号，结果逐项展示；批量预览标记可处理、已是该角色、无权处理及已失效账号。应用只处理管理员明确选中的可处理项，预览后任一目标变化时选定批次整体返回 409，重新预览；不在管理员未知情时执行半批。

如果管理员在用户详情点击“调整权限”，界面先明确选择“修改当前角色，影响全部使用者”或“复制为新角色，仅替换该用户”。本期不在用户身上叠加隐藏的单独权限；仅调整一人时，使用复制角色并替换主角色的同一流程。

### 4.4 停用与迁移

首版只允许角色无有效引用时停用；有引用时提示逐个替换普通账号、清除岗位默认角色、撤销邀请后重试。以下整批迁移向导为后续增强，不能作为首版强依赖。

无有效引用的角色可直接预览停用。有使用用户、岗位默认映射或未使用邀请时，列出这些引用，提供：

1. 将普通用户和岗位默认映射迁移到一个有效角色，撤销旧邀请后停用。
2. 停用相关普通账号，清除岗位默认角色并撤销邀请后停用。

迁移需要用户管理、角色分配及对应岗位维护权；停用账号需要账号管理权。缺少任一能力时，提示需由具备完整权限的管理员处理，不先改一部分对象。引用涉及所有者或其他管理员时仅所有者处理，且不能使所有者角色失效。

本期整批迁移上限 100 个账号；超过上限先按批次迁移用户，最后检查无引用再停用。不做未提供进度和失败恢复的后台迁移。并发新增引用时，在同一事务中锁定角色并复核；角色进入停用后不得再被分配或用于新邀请。

停用成功后，旧角色授权不参与任何用户业务鉴权；历史记录保留，不能自动恢复未处理的账号或邀请。

### 4.5 恢复、应用模板与归档

首版支持模板应用与发布历史查看；指定历史版本恢复界面后续开放，但发布快照从首版开始保存。

恢复模板、应用模板和恢复某个历史版本都先生成新配置及差异，再走当前授权检查。旧版本有权限不表示现在仍允许授予；禁用领域包或超出当前委派上限的项必须列出并拒绝原样发布，管理员可显式调整后重试。

恢复不回滚用户角色分配、部门、账号状态和管理员委派。重新启用角色只启用已校验的配置，不自动重新挂回原用户，不恢复旧邀请。归档前必须已停用且无在用引用；归档后保留历史版本供查看、复制。

## 5. 管理边界与统一校验

| 校验对象 | 要求 |
| --- | --- |
| 组织与身份 | 当前账号、管理委派、组织均有效；管理能力实时回源 |
| 权限目录 | 业务角色只接受 BUSINESS；新增/调整差量检查可用目录和委派清单，保留只读历史项不代表重新授予；分配则检查完整有效配置 |
| 管理角色 | 角色在维护白名单中，或由管理员在“允许新建”的委派内创建；归档角色不可写 |
| 管理人员 | 所有受影响账号、邀请预约节点及岗位引用满足管理对象边界 |
| 共享角色 | 角色被范围外账号或其他管理员使用时，受限管理员不可修改其有效配置，即使当前只想改一个权限 |
| 范围包含 | 根据节点集合、支持的范围语义和目标用户计算，不能以 ORG/UNIT 等枚举大小比较 |
| 自身和治理身份 | 普通管理员不能给自己增加业务权，不能修改自己或别人的治理委派；由所有者处理 |
| 状态与版本 | 预览、应用均检查；角色版本、组织授权版本或人员版本变化则重新预览 |

受限管理员遇到被其他节点共用的角色时，可复制到新角色，再为自己范围内用户申请或执行替换；不能暗中把一次修改拆成部分用户生效。同一角色的一项权限配置对所有使用者一致。

管理身份的扩大、缩小或撤销更新有效授权版本；期限到达按当前服务端时间直接失效，不依赖定时任务先更新版本。每次请求、变更应用和后台动作检查期限，流在每次受保护输出前重查；到期事件用于主动断开和 UI 刷新，不能作为唯一检查。无法收回已经发送的内容，“立即”指后续受保护动作不再获准。

上限缩小后，不回滚管理员过去合法创建的角色及已分配业务授权；界面展示存量超限配置并限制后续操作。需要回收既有用户权限时，由所有者另行执行角色撤权和分配调整，避免误认为“撤销管理员”已撤销其历史授出的全部权限。

## 6. 业务示例

所有者将李同学设为组织管理员，允许维护全组织普通账号、角色，并授予活动与排班目录中的明确操作权限；没有把党务或平台权限纳入委派。

李同学从空白建立“活动协调员”，配置查看本组织活动、编辑本节点及下级活动与任务、查看与管理本节点及下级排班。活动主办节点等数据已完成迁移，编辑粒度明确包含活动编辑而非仅任务分配。预览启用后，分别为文秘部两位普通成员更换角色，明确替换他们原来的“干事”角色。

此后组织决定协调员只能查看排班：李同学取消“管理排班”，预览显示两名用户失去排班编辑能力，保存后下一次写请求即拒绝，灵思的排班写工具也不再可用。其他组织以及本组织其他角色的授权不变。

李同学尝试给角色勾选党务敏感字段读取时，页面显示“超出管理员授权范围”；直接构造接口请求同样拒绝。如果确需该能力，由所有者扩大明确委派范围，再执行角色变更。

## 7. 状态、数据与审计

在总方案模型上补充：

| 对象 | 明确字段 / 规则 |
| --- | --- |
| `org_role_delegation` | 用户、组织、管理能力、管理节点集合、可维护/分配角色、是否允许新建、可授权权限与范围、期限、状态、版本；仅所有者可维护 |
| `sys_role` | `DRAFT / ACTIVE / DISABLED / ARCHIVED`；组织内唯一名称和永久唯一编码、来源类型、可选模板及来源角色 ID、版本 |
| `role_permission` | 仅生效授权；权限调整必须原子更新并增加授权版本 |
| `org_authorization_change` | 组织、操作者、动作、目标、拟议差量、基线版本、影响摘要、过期时间、状态、幂等键与应用结果；预览有效期建议 5 分钟 |
| `role_revision` 与工作稿 | 新建、启用及停用角色的完整工作稿和不可变发布快照；以指针及 `draft_version` 管理，详情见 §7.1；工作稿不注入有效权限 |
| 审计 | 动作、角色和用户、前后差异、操作者及委派来源、原因、请求标识、时间、成功或拒绝；不存密码或令牌 |

### 7.1 工作稿、发布版本与临时预览的明确关系

以总方案新增的 `role_revision` 作为唯一配置版本来源：

1. 每角色最多一个可编辑工作稿，状态 `DRAFT`；保存完整权限、范围、领域包授权版本及目录语义版本快照，用 `draft_version` 防覆盖。
2. `sys_role.draft_revision_id` 指向工作稿，`current_revision_id` 指向不可变的 `PUBLISHED` 快照。新建角色没有当前发布版本；启用/停用角色都可保存新工作稿。
3. 预览记录绑定确定的工作稿版本、当前发布基线和相关身份/对象版本；预览可过期清理，不用作历史版本仓库。
4. 应用时再鉴权，将工作稿冻结为发布快照，原子更新当前指针、`role_permission` 查询投影、授权版本及审计。后续编辑创建新工作稿，不修改旧发布记录。
5. 角色状态决定是否采用发布配置：停用角色即使保留发布快照也不产生业务授权。重新启用检查工作稿或选定发布配置的当前合法性，不能绕过领域包版本。
6. 后续历史恢复将旧快照复制成新工作稿，按当前目录、领域包和委派检查后发布新版本；不从临时预览或审计差异倒推，也不修改旧版本。

审计用于解释“谁改了什么”，发布快照用于复现“当时完整配置”，两者不能互相替代。领域包版本机制见总方案 §8；角色生效投影中的领域权限携带 `pack_activation_version`，停用再启用后旧版本失效。

变更状态为 `PREVIEWED → APPLIED`，过期或基线变化不能再应用；作废状态可按需记录。预览与应用绑定当前组织及当前操作者，不向另一管理员转交可执行凭证。

应用时锁定相关组织、委派、角色和目标用户，按统一顺序复核并原子提交配置、授权版本和成功审计。重复提交同一幂等请求返回已应用结果；伪造相同键但更换内容则拒绝。前端不得在网络超时后盲目创建第二次变更，应查询原变更结果再决定重试。

历史变更查看按当前管理范围裁剪，不能通过审计读取范围外用户信息。总影响人数可以作为无法执行操作的提示，但不展开不可管理账号的姓名和详情。

## 8. 接口与交互契约

统一以当前登录组织为上下文，不接受前端 `orgId` 作为可信边界。普通角色写入和治理委派分开；主角色不得承载可自行扩展的管理能力。

| 接口草案 | 用途 |
| --- | --- |
| `GET /api/auth/me` | 增加业务权限、管理能力摘要及授权版本；来源分别说明 |
| `GET /api/orgs/current/management-capabilities` | 返回可用管理动作、可管理边界、可授权目录及受限原因 |
| `GET /api/roles`、`GET /api/roles/{id}` | 动态列表与详情；含版本、状态、来源、人数及后端计算的可操作能力 |
| `POST /api/roles` | 保存空白/模板/复制来源的草稿，支持幂等键 |
| `PUT /api/roles/{id}` | 改名称说明；校验角色版本，不改状态和生效授权 |
| `PUT /api/roles/{id}/draft` | 保存新建、启用或停用角色的工作稿，检查 `draftVersion`；返回工作稿 ID 及新的工作稿版本 |
| `DELETE /api/roles/{id}` | 删除可安全删除的未启用草稿；其他角色不物理删除 |
| `GET /api/roles/{id}/users` | 返回可见范围的使用用户；是否可完整管理另行返回 |
| `GET /api/permissions/catalog` | 权限中文说明、范围、依赖、领域包及可编辑能力 |
| `POST /api/roles/{id}/change-previews` | 预览发布、调整授权、停用、重新启用、归档、模板应用或历史恢复 |
| `POST /api/users/role-change-previews` | 预览一个或一批账号的主角色替换，可含同次调岗 |
| `GET /api/orgs/current/authorization-changes/{id}` | 查询本人变更预览、期限和最终应用结果 |
| `POST /api/orgs/current/authorization-changes/{id}/apply` | 使用当前身份重查并应用变更；带幂等键 |
| `GET /api/users/{id}/effective-permissions` | 业务和治理权限解释；仅限管理范围 |
| `POST /api/users/{id}/permission-checks` | 输入已注册操作与具体资源，返回授权解释，不返回敏感正文 |
| `GET /api/roles/{id}/changes` | 角色审计和不可变发布版本；历史恢复动作后续开放 |
| `GET/PUT /api/orgs/current/role-delegations/{userId}` | 所有者查看或设置管理身份、上限与期限 |

权限修改请求应提交明确的增加、调整和撤销操作，并携带角色版本；服务器在基线配置上应用差量，再输出完整预览。省略某项授权表示不修改，显式撤销才删除，避免受限管理员丢失只读授权。

有效授权仅通过同一变更服务发布，不保留独立的“整体替换权限”写入口。模板应用、后续历史恢复、角色停用和批量替换也复用此服务，不在 Controller 各写一套规则。

保存无变更时前端禁用按钮，服务器也返回无需变更。403 展示当前失去的管理能力，409 展示配置已更新并保留可重新编辑的表单；参数错误精确定位权限及范围，404 不透露其他租户对象存在性。

## 9. 与现有页面及实施阶段的衔接

当前 `PermissionManage.tsx` 是固定角色列表、权限树及全局恢复入口；`UserList.tsx` 仍有基于 `roleLevel` 的管理按钮和分配过滤。应先完成总方案 P0/P1 的租户角色隔离，再用本业务替换这些入口，不能先扩展前端菜单就开放全局授权。

前置批次先完成：治理分类与委派来源、租户角色隔离、角色码全局唯一约束迁移、业务资源节点/负责人映射、所开放范围的谓词、角色宏/级别/敏感字段判断替换，以及页面/API/知识源/工具一致性测试。未完成前，只允许内部草稿，不对用户宣布自定义角色可用。

首版批次在前置通过后实现：所有者/全组织管理员、明确的业务可授权清单、动态角色列表、空白/复制创建、工作稿和发布快照、差量编辑与单用户完整分配检查、无引用角色停用及审计。到本批次才验收创建—配置—发布—使用闭环；新模板初始化可复用已验证复制服务。

增强批次再开放：节点/角色受限委派、多种管理员预设、批量分配和停用迁移、具体对象诊断、历史恢复、所有者交接与平台管理界面。引用检查、账号保护、期限检查与领域包版本门禁不后置，首版即执行。

本业务不要求新增角色继承、用户级权限覆盖、多角色叠加或审批工作流；这些不影响管理员本期完成角色和权限管理。
