# PAMS 角色权限与租户管理：首版落地记录

日期：2026-10-15。依据已评审的[总方案](PAMS-用户角色权限与多租户管理设计方案-v1.md)与[管理员业务方案](PAMS-管理员角色权限管理业务设计-v1.md)，在 `design` 分支当前工作区实施。本文记录实际代码边界；两份设计文档中的增强功能不因本次实施自动成为已交付能力。

## 已实现的业务闭环

管理员通过“角色与权限”页面维护本组织角色：空白创建、从系统模板创建、复制已有角色、修改名称说明、编辑权限工作稿、预览并发布、查看使用用户与发布历史。角色状态为草稿、启用、停用、归档；存在有效账号、岗位或未过期邀请引用时不能停用或归档。未发布草稿可以通过接口删除。

用户继续采用一个业务主角色。管理身份单独存储：所有者可委派组织管理员，指定业务可授权清单及有效期，也可撤销管理身份；委派更新校验配置版本，拒绝覆盖其他会话已修改的配置。业务角色名称和历史级别不会自动产生治理权限；委派管理员可以授予自己没有业务访问权、但在可授权清单内的操作。其他管理员、所有者和管理员自身属于受保护对象，普通委派不能修改其角色或管理身份。

权限工作稿使用明确的 `SET / REVOKE` 操作及工作稿版本；省略项保留，空操作不清空配置，治理权限、未知权限和不支持的范围拒绝写入。工作稿不参与运行鉴权；发布前检查依赖、授权上限和当前版本。发布产生不可变快照，并在一个事务中更新角色生效投影、组织授权版本与审计。

用户主角色替换采用单用户预览及应用接口，完整检查目标角色的有效业务授权。预览绑定组织、操作者、基线版本和五分钟期限；应用时重新鉴权，重复应用返回原结果。提供原变更查询接口，供超时后核对执行结果。用户管理表单中的角色替换也复用该预览流程。

管理端可查看用户有效业务权限、治理能力来源和最近一百条治理记录。历史恢复、多对象批量迁移和资源级权限诊断尚未开放。

## 数据模型与迁移

新增 Java Flyway 迁移 `V37__tenant_authorization`，不修改历史迁移。H2 与 MySQL 的索引删除及列修改语法分别处理。

| 对象 | 实际实现 |
| --- | --- |
| `sys_role` | 租户角色实例；编码由全局唯一改为组织内唯一，新增状态、说明、配置版本和工作稿/发布快照指针 |
| `role_grant` | 当前已发布的业务授权投影，主键为组织、角色 ID、权限 ID；保存范围和领域包授权批次 |
| `role_revision` | 工作稿及不可变发布快照；工作稿版本用于并发控制 |
| `org_role_delegation` | 组织管理员治理能力、显式可授权清单、状态和可选到期时间 |
| `org_domain_pack` | 领域包状态与启用批次；关闭再开启不恢复旧批次授权 |
| `org_authorization_change` | 预览、基线、到期时间与幂等应用结果 |
| `org_audit_log` | 角色创建、元信息修改、工作稿、发布、角色分配及委派变更记录 |
| `role_template / role_template_grant` | 模板与模板授权快照，只作为创建起点，不驱动既有角色动态继承 |
| `authorization_bootstrap` | 存量治理身份转换的单次执行标记，避免重启后恢复已撤销委派 |

**对逻辑设计的物理映射调整**：两份设计中“重构后的 `role_permission`”在代码中命名为 `role_grant`。原 `role_permission` 保留为只读的旧授权迁移来源，运行鉴权不再查询它；旧全局保存/恢复接口返回 409。这样保留迁移比对依据，也避免旧角色字符串写入污染租户授权。

授权投影和快照均具有引用 `(org_id, role_id)` 的复合外键，投影还关联权限目录。迁移为跨组织共享旧角色 ID 的账号建立租户实例并重映射。迁移保留既有角色宏曾表达的内容管理、受限知识及敏感字段能力为显式权限；原 STAFF 无法进入的党务入口不因旧名义授权被放开。

启动初始化将旧的显式账号/权限管理授权转换为治理委派。仅在没有所有者且恰有一个有效旧权限管理员时填充所有者；多个候选不会任意选择。无有效所有者的组织输出错误日志，必须在迁移验收时核验并修复归属，不能据此认定该组织初始化完整。

## 访问控制接入

- JWT 每次请求查询账号、组织状态及当前有效授权，不再注入固定 `ROLE_*` 宏。`/auth/me` 分别返回业务权限、治理能力、所有者标记、主角色和组织授权版本。
- 角色、账号、组织和邀请写操作校验当前组织与目标归属；邀请的角色须在当前可分配清单中，节点须属于当前组织。
- 既有业务读取入口增加操作权限检查；文章、新闻、敏感党务字段、文件读取及 Agent 工具从固定角色判断改用明确权限。仪表盘、活动详情等聚合接口也按子模块权限裁剪，不能作为旁路。
- 异步 Agent 线程传播可信组织上下文并在结束后清理。缺少上下文时在提交阶段拒绝，避免静默落入默认租户或留下永不完成的异步任务。
- Agent 工具与知识问答执行时刷新权限；输出流校验组织授权版本，变更后停止旧流的后续输出。
- 知识库台账、全文详情、统计和个人检索记录按当前来源权限过滤。分页总数只计算可见数据；历史检索命中明细重新检查来源访问权。

普通文件仍保留本人及同部门对象约束；跨部门读取需要 `file:org:read`，敏感文件需要 `file:sensitive:read`，两者均依赖 `file:view`。这些权限承接旧文件读取规则，与党建领域包分开，避免用 `material:download` 无意放大普通成员的文件可见范围。

## 本期明确限制

1. 权限配置仅开放 `ORG`（本组织全部）范围。`UNIT_TREE / UNIT / SELF / ASSIGNED` 等范围未实现。新增的资源归属字段只是后续基础，不能视为已经回填并支持对应范围。
2. 首版委派固定为全组织管理员预设；不提供节点边界、可维护角色白名单、多种管理员预设或多角色叠加。
3. 固定密码重置入口返回 409，前端移除对应按钮。新账号必须提供至少八位初始密码；现有账号密码不批量修改。一次性密码设置凭证及安全交付流程后续实现。
4. 旧直接开户接口继续返回 409。批量开户现已接入逐人授权预览与一次性设密凭证交付，恢复用户管理和成员账号关联页入口；详情见《PAMS-花名册批量开户流程》。花名册业务数据导入不受影响。
5. 所有者双向确认交接、平台身份与治理后台、组织草稿供给重试、平台暂停与业务提交共用的全局写门禁、拒绝操作的完整审计及审计导出尚未实现。已有组织注册流程仅接入租户角色初始化，不能视为总方案中两阶段供给的完整实现。
6. 知识库台账先在当前租户枚举候选元数据，再回源计算可见 ID 并过滤分页；满足本期权限正确性，需要在大数据量下进一步优化查询与性能。
7. 真实 MySQL 迁移、存量数据影子比对、组织所有者清单及生产切换尚未验收。H2 测试不能替代这些工作。
