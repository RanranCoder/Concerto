# 灵思 Agent UI 与后端业务审计

日期：2026-10-23。范围：灵思 Markdown/角标/资料预览、前端会话与字符流状态、知识库策划书来源、任务确认/取消、流归属、历史引用权限与模型上下文。此报告区分已复现修复、代码审计发现和未验证边界；不是对全部工具业务的安全认证。

## 用户截图的原因

1. **流程、预算显示 JSON**：`ActivityPlanSource.field()` 直接返回业务表中 `flow`、`budget` 的序列化数组，`toDoc()` 原样入索引；`ScoredChunk.snippet()` 只压平换行并截断，前端也按普通段落展示。因此内部 `step/detail/item/quantity` 泄露成了阅读内容。不是用户数据写错。
2. **角标底色先出现、正文再次逐字显示**：上一轮新增的 `useStreamReveal` 仅给文本节点做动画。角标背景在父元素上，数字和底色没有一起显现；收官下发引用后，`[3]` 被替换成 `3`，字符位置变化又让后续正文被误判为新增。此缺陷来自本次会话上一轮加入的动效实现。
3. **非连续引用编号不可点**：服务端只回填实际使用的编号，例如只引用 `[3]` 时数组只有一项；前端此前按 `citations.length` 推断合法范围，错误地只允许 `[1]`。

以上均已修复。角标作为整体动画，差异比较保留原始 `[n]` 位置；合法编号取实际引用集合并排除已撤权项。历史答案直接展示，不重播。

## 已修复的审计发现

| 优先级 | 问题与影响 | 修复位置与行为 |
| --- | --- | --- |
| P1 | 登录用户可尝试中止其他人的流 | `AgentController.abort` 调用 `AgentEventPublisher.abortOwned`，先检查所有者；未知 ID 不创建中止状态 |
| P1 | 资料撤权后仅清引用片段，历史回答/推理仍可能包含原文；下一轮上下文还会带回旧回答 | `ConversationStore` 对含不可见引用的回答隐藏全部派生正文、推理与工具明细，并清理引用标题；`AgentOrchestrator.buildContext` 同样调用权限复核。保留数据库原始历史，不改写审计记录 |
| P1 | 确认接口未调用已有的 24 小时过期判断 | `TaskGate.confirm` 在任务抢占前拒绝过期清单 |
| P1 | 取消与确认并发时，读后 `save(CANCELLED)` 可覆盖 RUNNING/SUCCESS | 仓储新增按任务、所有者和待处理状态限定的原子更新；手动取消及旧清单替换均使用它。H2 集成测试验证 RUNNING/SUCCESS 不会被取消覆盖 |
| P1 | 登出后，迟到的回答/会话列表请求可回写旧账号状态 | `reset` 使请求版本失效；回答和会话列表响应均检查版本 |
| P2 | 已绑定流之外的正文事件绕过普通事件过滤，可清空当前回答或混入字符 | 增量缓冲携带 streamId；入口与落地都检查归属，忽略已完成流的迟到事件 |
| P2 | 切换会话后 thinking/activeStreamId 残留，输入可能持续被锁定；A→B→A 时旧 A 请求仍能覆盖新 A | 切换时清理实时状态，历史响应同时检查请求版本和会话 ID |
| P2 | 停止操作等待网络返回后才隔离旧响应，存在竞态 | 先使本地请求失效并停止渲染，再调用中止接口 |
| P2 | MESSAGE_DONE 未关闭流式占位，REST 到达前仍可能接受迟到字符 | 收官使用权威正文并关闭流式状态，随后 REST 补齐消息 ID、工具和提供方等元数据 |
| P2 | 工具下线时先抢占再查工具，任务可停在 RUNNING；只读确认会消耗原清单 | 工具查找及只读/资料模式检查移到抢占之前 |
| P2 | 表单转清单、清单反序列化时丢失 preview | 保留 `preview`，避免提交补全后无法通读待写入内容 |
| P2 | 策划 JSON 直接入索引与引用；历史截断 JSON 难读 | 新增 `PlanSectionText` 在入索引前格式化，KB 出网链路兼容完整旧 JSON；前端对旧引用快照只恢复完整条目，明确标示截断，不编造缺失内容 |

资料撤权时暂时隐藏整条派生回答，是因为系统没有逐句来源映射，无法可靠地只删其中几句话。重新提问会按当前权限检索。

## 仍需处理的代码审计发现

这些项未在本次修复中宣称解决。

| 优先级 | 证据与触发条件 | 待处理方向 |
| --- | --- | --- |
| P2 | `AgentEventPublisher` 的 buffers/owners/authorizationVersions 按 streamId 持续累积；streamBufferSize 仅限制单条流事件数，`clear` 不移除这些映射且编排器未调用它 | 为已结束流增加有界容量及 TTL，保留补拉窗口；需要覆盖重启和历史补拉行为 |
| P2 | `KbPrompts.buildUserMessage` 按 4000 字和 8 片截断实际 prompt，`KbPipeline` 却用整个 safe 集合回填引用 | 先生成唯一的实际片段集合，再统一用于编号、prompt 和引用校验。当前允许引用模型本轮未收到的后部片段，影响证据可信度 |
| P2 | `AgentLlmCaller.callLlm` 没有传输级取消；标准模式在轮次边界检查中止，KB 分支缺少相同检查 | 停止渲染不等于模型请求立即停止，也不保证立刻停止计费。需要可取消的 provider 请求及 KB/协作收官中止检查 |
| P2 | 新一轮首个事件到达前 activeStreamId 为 null，协议没有由客户端发起的 requestId 贯穿所有普通事件 | 同账号多个窗口同时发起请求时，仍可能先绑定到另一个窗口的新流；已知旧流和已绑定外来流已隔离 |
| P2 | `TaskGate.supersedePending` 与创建新任务之间没有会话级串行化 | 同会话并发发起两次生成，仍可能产生两张待确认清单；本次原子更新解决的是取消覆盖执行状态的问题 |

检索质量另有边界：关键词命中历史策划书，不代表找到了制度性“审批要求”。本次没有用真实模型验证截图那一轮回答的结论，也没有将历史活动案例自动认定为审批规范。
