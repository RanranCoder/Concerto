# V6 组织架构落地记录

日期：2026-10-18

## 已落地

- `/org/structure` 使用已确认的「左侧架构树 / 右侧节点工作面」，支持多层搜索、展开收起、节点增删改、负责人选择、直属账号、节点信息与组织资料。
- 新增独立的节点与组织资料编辑表单，新增不复用当前节点的输入；校验重名、必填、长度、排序和主题色，失败保留输入并允许重试，保存期间阻止重复提交。
- 手机端折叠架构导航，选中节点后自动收起；沿用全站明暗主题、字号和圆角令牌。
- 创建组织继续使用原来的多层树与注册接口；成功后仅携带组织 ID、名称、管理员用户名返回登录。只有登录账号、组织均与创建结果匹配且具备组织管理权限时，才进入组织架构并显示后续操作提示；普通登录仍进入工作台。
- 登录页与管理页复用 `LoginOrganization` 展示组件，组织资料修改后刷新组织 store；登录展示依然不决定账号租户归属。旧组织未配置扩展包时，使用 store 原有的全部启用兼容规则。
- 成员管理和用户管理接收 `deptId` 查询参数，关联入口带入当前所选部门。花名册、账号归属、主角色与管理员身份保持各自管理边界。
- 邀请码放在次级入口，仅使用当前操作者可分配的角色，展示部门和有效期，并明确尚未开放兑换入组入口。

## 接口和数据

新增 `GET /api/orgs/current/structure`，由 `org:manage` 或 `org:structure:manage` 授权。返回当前组织的完整架构和最小账号目录（ID、用户名、姓名、部门 ID、角色名称、状态），不返回密码、电话等字段。组织归属显式过滤，禁用账号仍计入归属关系；不以分页列表冒充全量统计。

现有注册、节点维护和组织资料接口继续使用同一组 Department / Organization 记录。注册和日常维护共用节点类型、50 字长度及组织内名称唯一的口径；服务端同时校验负责人须属于当前组织且为正常账号，任命不会修改账号角色。

删除在服务端检查下级节点、全部关联账号（含停用和软删除）、成员名册、任务、材料、排班、无课表、知识库、活动归属、通知、邀请与部门群聊等历史引用。节点改名保留原 ID，并同步已有部门群聊与无课表中的冗余名称。

路由和菜单允许组织管理或架构管理权限进入；编辑组织资料、维护节点、生成邀请分别按各自权限控制，服务端继续校验。

## 数据库迁移

新增 Java Flyway 迁移 `V39__department_tenant_unique`，将节点名称约束统一为 `(org_id, name)`。

旧 MySQL V34 使用 `(org_id, parent_id, name)`，与前端禁止组织内重名的规则不同，且根节点的空父 ID 无法提供预期的唯一保护；H2 的 V34 未放宽旧全局唯一约束。V39 在两个数据库中采用一致的规则，允许不同组织都拥有「组织部」。已有 MySQL 数据若包含同一组织中的历史重名，需先核实并处理这些名称再应用该约束；迁移不自动删除或合并节点。

本轮完成代码与测试，未重启正在运行的业务后端，也未对开发或生产库执行迁移。后端下次启动会通过 Flyway 加载 V39 和新增接口。
