# 协奏权限管理更新方案 v2（已确认）

日期：2026-10-25  
状态：用户已确认一期并授权实施；实际交付与验证边界见[一期落地记录](PAMS-权限管理-v2-落地记录.md)。方案中的二期及增强能力不代表已实现。  
依据：当前 `Concerto` 工作区代码、现行业务流程，以及 2026-10-15 的角色权限首版设计和落地记录。

## 1. 方案结论与本次建议范围

将现有“角色与权限”升级为围绕职责配置的权限管理工作区：管理员先理解角色负责什么，再配置业务操作，检查受影响人员，预览后发布；同时能查清某个人为什么能做或不能做某项操作。

继续采用“一个业务主角色 + 独立管理身份 + 资源关系及业务状态约束”的模型。组织架构、岗位名称、历史角色级别均不直接产生权限。沿用已有租户角色、工作稿、发布快照、变更预览及治理审计，重点更新业务权限目录和管理流程。

**建议本次先实施一期：完整更新页面、拆分关键业务操作、完善发布影响与权限解释，并统一页面、接口、灵思和知识库的执行口径。** 一期保持已实现的 `ORG` 授权范围，同时保留各业务已有的作者、指定审核人、本人等对象约束，不把 `ORG` 描述成“可以操作所有对象”。

二期再开放可配置的本人、指派对象、组织节点范围；前提是资源归属、账号关联及查询过滤已经完成。多业务角色叠加、直接给个人额外授权、平台治理、所有者交接和多人授权审批不纳入本次一期。

这不是重新恢复“指导老师有全部权限、部长有一组固定权限”的旧模型。指导老师、主任、干事等名称仍可保留为组织自定义角色或模板名称。

## 2. 当前实际情况与需要解决的问题

### 2.1 已有能力应当复用

| 已有基础 | 当前代码边界 | 更新策略 |
| --- | --- | --- |
| 组织内角色 | 可创建、复制、从模板创建；草稿、启用、停用、归档 | 保留生命周期，补全列表、详情和操作解释 |
| 工作稿与发布 | 工作稿不生效；预览后发布；版本校验、五分钟预览、幂等应用 | 保留，完善差异和影响预览 |
| 单业务主角色 | 用户只持有一个业务主角色 | 一期继续，兼任通过组合职责角色处理 |
| 独立管理身份 | 所有者与有效管理员委派决定治理能力；可授权清单与业务访问分离 | 保留，明确呈现管理能力来源及上限 |
| 数据范围 | 权限目录和服务端仅开放 `ORG` | 一期如实呈现；二期按业务逐项开放 |
| 资源业务规则 | 策划书作者／指定审核人、文件本人／同部门及敏感权限等 | 作为额外约束保留，统一参与鉴权 |
| 灵思与知识库 | 工具检查业务权限；检索回源复核；任务和成果有归属及实时权限约束 | 新权限必须覆盖这些入口 |
| 账号供给 | 花名册开户已使用授权预览和一次性设密流程 | 继续复用，与成员资料权限分开 |

### 2.2 从代码可确认的主要缺口

1. **页面仍偏权限码清单。** 当前页是角色按钮列表、分页权限表和几个弹窗，缺少业务分组导航、职责说明、改动筛选、有效配置与工作稿并列理解、影响人员摘要。发布历史只展示版本、时间和数量，难以回答“这次到底改了什么”。
2. **活动权限承载过多职责。** `activity:edit` 同时参与活动状态、任务增删改及进度、策划编写提交、议程和评分写操作的授权。无法只让某人处理任务而不编辑整个活动。
3. **排班生成、维护、发布边界不清。** 活动排班生成允许 `schedule:generate` 或 `schedule:manage`，发布仍由 `schedule:manage` 控制，值班表导出也复用管理权限。管理员无法清晰配置“只生成草稿”“可发布”“只导出”。
4. **本人考勤与管理他人考勤交叉。** 考勤中心的人工修正／补签允许 `attendance:manage`、`checkin:manage` 或 `schedule:check`；旧种子也曾向干事授予 `attendance:manage`。不能只根据角色名称判断哪些账号应保留修正能力，需要迁移核对。
5. **宣传管理打包。** 推文创建、审核和管理分支使用 `content:manage`；新闻稿写操作使用 `news:manage`。推文还具有作者操作规则，需要同时表达职责和作者关系。
6. **权限“已配置”不等于“当前有效”。** 领域包关闭或授权批次过期、角色失效、账号停用均会改变实际结果；当前只读说明把“领域包未启用”与“超出可授权清单”合并，难以处理。
7. **依赖规则过于通用。** 服务端主要按同前缀 `:view` 推断依赖，不能完整表达 `kb:read`、跨模块依赖和范围关系。
8. **执行结果可解释性不足。** 有效权限接口已经存在，但只列码和治理来源；缺少“所选操作 + 具体对象”的拒绝原因。页面按钮也未充分解释受保护角色、有效引用等限制。
9. **前端刷新策略需要补齐。** 当前主要在启动／刷新和本页变更后刷新本人权限；其他在线会话需要及时失效和更新入口，后端仍必须以请求时的当前权限为准。

以上为静态代码梳理，不等于已完成运行环境安全审计。旧注释中存在固定角色表述，不能把注释当作当前运行规则。

## 3. 业务模型与统一判定规则

### 3.1 把三个问题分开

| 问题 | 配置来源 | 示例 |
| --- | --- | --- |
| 这个人可以做什么业务操作？ | 业务主角色的已发布授权 | 编写策划、发布排班、导出成员 |
| 这项操作能作用于哪个对象？ | 操作范围 + 资源关系 + 业务状态 | 本人班次、指定审核的策划、可编辑状态的稿件 |
| 这个人可以替谁配置什么权限？ | 所有者身份或管理员委派 | 可维护普通角色；仅可授予活动相关操作 |

组织管理员可以配置某项业务权限，不代表他本人可以读取该业务内容。拥有业务审核权，也不代表可以设置其他人的权限。

### 3.2 业务操作必须同时满足的条件

```text
允许操作 = 账号有效、组织有效且归属一致
        ∧ 当前业务角色有效且已发布该操作权限
        ∧ 对应业务能力／领域包有效且授权批次有效
        ∧ 对象位于允许范围内
        ∧ 满足作者／负责人／指定审核人等必要关系
        ∧ 当前业务状态允许该操作
```

一期 `ORG` 仅表示不额外施加节点范围过滤；作者、审核人、文件归属和状态规则继续生效。例如，拥有全组织的“审核策划”资格，仍只能审核分配给自己的当前待审版本。

治理操作使用独立规则：有效治理能力、管理对象边界、可授权清单、受保护身份、当前版本均须通过。不能通过给普通角色勾选治理权限获得管理身份。

系统所有者可管理组织授权，但业务数据访问仍来自自己的业务角色。新建敏感权限不因身份或职位自动授予所有人。

### 3.3 基础个人能力的取舍

一期继续把查看自己的通知、通知已读／偏好、修改本人密码及有效登录身份下的个人资料入口视为基础能力。通知正文和业务跳转仍按来源权限裁剪。旧 `notification:view/preference` 目录标记为基础能力，不再制造“取消勾选却仍可访问”的假配置。

本人排班、本人考勤、本人课表属于业务能力，使用明确的本人操作权限。账号没有班次或课表时返回空状态，不用宽泛的全组织查看权限兜底。

灵思对话入口保持当前有效登录账号可用；是否可调用某工具、读取某资料、执行某操作由对应业务权限决定，不新增笼统的“AI 全部操作权”。

## 4. 一期权限目录规划

权限点按用户理解的工作场景分组。下列新增码均为**拟议设计**，需要确认后才创建并接入；现有码不因本文出现即被停用。开发时须产出逐接口、按钮、工具和知识源映射表，未接入的操作不在配置页伪装成可授权项。

### 4.1 活动筹备与执行

| 业务职责 | 一期建议权限 | 明确边界 |
| --- | --- | --- |
| 查看、创建、编辑、删除活动 | 保留 `activity:view/create/edit/delete` | `activity:edit` 收敛为活动基础信息；删除单独授权 |
| 推进活动阶段 | 新增 `activity:transition` | 仍校验阶段转换条件；不因有权限跳过必要流程 |
| 分配活动承办部门 | 保留并核实接入 `activity:assign` | 只改变承办关系，不自动改变账号权限 |
| 查看／维护议程 | 新增 `agenda:view/manage` | 与活动基本信息修改分开 |
| 查看／维护任务、更新执行进度 | 新增 `task:view/manage/progress` | 维护任务结构与更新进度分开；一期进度授权仍为 ORG，并清楚提示影响，二期再限定本人指派任务 |
| 查看／编写／提交／审核策划 | 新增 `plan:view/edit/submit/review` | 修改、提交限当前版本作者；审核限指定审核人和待审状态；选择审核人随提交能力提供 |
| 查看／维护评分 | 新增 `score:view/manage` | 评分规则和成绩操作作为一期同一管理职责，不附着活动编辑 |
| 查看／编辑座位、管理座位模板 | 保留 `seat:view/edit/template` | 模板使用、保存和删除沿用现有能力边界，目录解释具体覆盖动作 |
| 查看签到、维护应签名单及签到、导出 | 保留 `checkin:view/manage/export`，补齐真实导出链路检查 | 扫码公开入口使用活动令牌和核验规则，不通过免登录扫码获得后台名单读取权 |

策划版本读取沿用当前专门规则：当前版本受作者／指定审核人限制；历史版本沿用现有可见性规则并在目录中明确说明。任何希望收紧历史版本的调整需单列影响，不借页面重构暗改。

### 4.2 排班、课表与考勤

| 业务职责 | 一期建议权限 | 明确边界 |
| --- | --- | --- |
| 查看组织排班 | 保留 `schedule:view` | 与“我的排班”分开；二期再按组织节点裁剪 |
| 查看我的排班 | 新增 `schedule:self:view` | 仅服务端确定的本人账号关联，不接受请求方传入任意人员 ID |
| 维护排班草稿 | 保留并收敛 `schedule:manage` | 创建、调整、删除草稿；已发布班次调整须进入发布影响流程 |
| 自动生成排班草稿 | 保留 `schedule:generate` | 生成不等于发布；灵思预览和确认生成也遵守该边界 |
| 发布／取消发布排班 | 新增 `schedule:publish` | 展示通知对象和已发布数据影响；已有排班调整不得绕过发布权 |
| 导出组织排班 | 新增 `schedule:export` | 数据范围不超过可查看范围 |
| 本人课表录入与查看 | 新增 `course:self:manage` | 本人数据；无课查询不自动开放他人完整课表 |
| 批量导入课表、维护学期参数 | 新增 `course:manage` | 与个人录入分开；视为包含个人信息的管理操作 |
| 查看组织无课信息 | 保留并明确 `schedule:free_table` | 只返回业务需要的空闲结果；个人原始课表读取仍受保护 |
| 本人打卡与本人考勤 | 保留并收敛 `schedule:check`；新增 `attendance:self:view` | 只能登记本人有效班次；服务端核验账号、班次和时间，不可替别人补签 |
| 查看考勤中心、人工修正及补签 | 保留 `attendance:view/manage` | 删除旧 `schedule:check`、`checkin:manage` 的人工修正放行分支；查看考勤修改记录要求查看该记录的资格 |

签到是活动到场记录，考勤是排班履职记录；两者可能联动，但一个管理权限不能自动成为另一个模块的人工修正权。

### 4.3 成员、党务与个人信息

| 业务职责 | 一期建议权限 | 明确边界 |
| --- | --- | --- |
| 成员查看、维护、导出 | 保留 `member:view/manage/export` | 查看与导出分开；导出不扩大行范围和字段范围 |
| 开通和关联成员账号 | 保留治理能力 `member:import_account` | 同时校验账号治理和目标角色可分配资格；不因能维护花名册自动获得开户能力 |
| 党务查看、流程、函调、录入 | 保留 `party:view/manage/letter/entry` | 仅党建领域包有效时可配置和使用；跨包不自动授权 |
| 党务敏感字段 | 保留 `party:sensitive:view` | 查看、导出、文件、聚合和知识引用统一应用脱敏规则 |

成员名单中的敏感字段应逐字段核查。确需新增独立敏感字段权限时，应有明确字段清单、后端脱敏及导出覆盖后再启用；一期不先放一个实际无效的勾选项。

### 4.4 宣传、档案、通知与知识库

| 业务职责 | 一期建议权限 | 明确边界 |
| --- | --- | --- |
| 查看推文与新闻 | 保留 `content:view` | 一期沿用共同读取资格，写操作分开 |
| 推文创建、编辑、提交、审核、标记发布、统计、删除 | 新增 `article:create/edit/submit/review/publish/stats/delete` | 作者关系与状态仍限制操作；编辑他人稿件须明确显示“管理范围内稿件”的含义；审核不能由编辑权隐含获得 |
| 新闻稿维护与发布 | 保留并收敛 `news:manage`；新增 `news:publish` | 维护草稿和发布分开；`news:manage` 不再隐含发布 |
| 材料查看、上传、预览、下载、删除 | 保留 `material:*` 现有五项 | 下载还需满足实际文件来源和敏感级别规则 |
| 模板查看、使用、维护 | 保留 `template:view/use/manage` | 使用模板不等于修改组织公共模板 |
| 素拓查看、手动加分、活动批量加分、删除 | 保留 `quality:*` 现有四项 | 批量动作预览对象和数量，写入仍逐项校验 |
| 公告查看、发布、管理 | 保留 `notice:view/publish/manage` | 管理包含哪些编辑、撤回或删除动作在目录逐项说明 |
| 群聊资料查看、维护、分类 | 保留 `chat:view/manage/category` | 统一菜单、路由和 API 的可见条件 |
| 文件读取 | 保留 `file:view/org:read/sensitive:read` | 本人／同部门、跨部门、敏感内容分别控制；业务附件仍服从来源对象权限 |
| 知识库查看、文档维护、索引维护 | 保留 `kb:read`；拆出新增 `kb:document:manage/index:manage` | 普通文档编辑职责不自动获得重建全组织索引的能力；索引统计只包含当前可见内容 |
| 受限知识 | 保留 `kb:restricted:read` | 不是读取所有业务数据的通行证，还要通过来源权限及字段规则 |
| 个人通知与偏好 | 基础个人能力 | 不提供查看他人通知权限；通知不能携带当前已无权读取的业务正文 |

`content:manage`、`activity:review`、`kb:manage` 等旧聚合码在迁移过渡后从普通编辑目录退出，不长期保留为绕过细分授权的另一条路径。

### 4.5 依赖与勾选逻辑

- 每个权限定义显式依赖，不再只用字符串前缀推断。例如 `plan:review → plan:view + activity:view`，`task:manage/progress → task:view + activity:view`，`kb:document:manage → kb:read`，`schedule:publish → schedule:view`。
- 勾选操作时提示依赖并一并加入本地工作稿。依赖超出可授权清单时，整体拒绝该次勾选并说明缺少什么，不偷偷扩大授权。
- 取消被依赖权限时列出受影响操作，用户确认后同步取消；后端独立验证依赖。
- 依赖只表达必要前提，不代表自动合并职责。发布排班不要求拥有自动生成权；审核策划不要求拥有编辑权。
- 导出、敏感字段、删除、发布、人工考勤修正标记为重点影响操作；勾选只修改工作稿，真正生效仍走统一预览发布。
- 新增权限只在明确迁移映射或主动发布后生效，不允许通过“模块全选”自动订阅未来权限。

## 5. 管理身份与授权边界

### 5.1 一期管理能力

沿用现有治理能力：角色查看、角色维护、授权发布、角色分配、账号查看／维护、组织配置、架构管理、邀请、治理审计、花名册开户。页面按当前能力显示入口，查看型账号不得看到可执行的编辑或发布按钮。

一期所有者仍使用现有“组织管理员”预设进行委派，不把暂未实现的受限账号管理员、受限角色管理员表现为可选项。委派页需分别展示：

1. 管理能力清单（一期预设实际包含的能力）。
2. 可授权的业务操作清单，与管理员本人业务权限分列。
3. 有效期、当前状态、最近修改人和版本。
4. 明确的保存前差异；撤销管理身份不撤销原业务角色。

细分管理预设、节点边界和可维护／可分配角色白名单列入二期。

### 5.2 防止误授权的规则

- 只在当前组织内操作；未知对象和跨组织对象不泄露其详情。
- 普通管理员不能修改自己、所有者和其他管理员的主角色／管理身份，也不能通过修改这些账号共用的角色绕过保护；页面提前给出需所有者处理的原因。
- 分配角色时校验**整个目标角色**的有效授权是否落在可授权清单内，而不是只比较新增项。
- 已有但超出管理员上限的角色权限可读、不可改，差量保存必须保留，不能因隐藏或未返回而意外删除。
- 所有者委派也要预览变更，保存时重新校验账号状态、领域包、版本和有效期；新增敏感权限不自动进入存量委派。
- 管理身份不是对恶意管理员的强保密边界。有建号和授角能力的受信任管理员可能通过其他账号访问其可授予内容；若要求多人制衡，应另立审批模型。
- 固定密码重置入口保持关闭；一次性本人设密及现有开户流程继续使用，不借本次更新恢复旧固定密码功能。

## 6. 页面与交互设计

入口保留 `/admin/permissions`，导航名称统一为“角色与权限”。顶层分为“业务角色 / 管理身份 / 变更记录”；有效权限查询从页面工具区和用户详情均可进入。非所有者的管理身份页只展示自己的有效委派和上限，不展示其他人的委派详情。

### 6.1 业务角色列表

提供角色名称搜索、状态筛选、已发布／有工作稿筛选。显示名称、职责说明、生效操作数、使用账号数、状态、工作稿提示和最后修改时间；来源标签仅在能可靠追溯时显示，不为旧数据编造来源。

空白创建、从职责模板创建、复制角色共用向导。模板只是创建起点，不绑定固定职位，也不会随模板更新改变现有角色。角色编码稳定，名称可修改。

建议提供活动统筹、任务执行、策划审核、排班维护、考勤核验、宣传编辑、宣传审核、成员维护、知识维护等职责模板。创建时可组合多个模板的业务操作，但最终仍生成**一个独立角色**；敏感查看、导出和删除不作为基础执行模板的默认项。旧组织角色不自动改名或替换为新模板。

### 6.2 角色详情与权限编辑

```text
角色与权限 / 活动协调员         启用 · 生效版本 6 · 使用 12 人
职责说明：维护活动筹备、任务和排班草稿       修改信息  复制  更多

权限配置 | 使用人员 | 发布历史

业务分组                 操作权限                  配置状态／说明
活动与策划               查看活动                  已授权
任务与执行               维护任务                  已选，待发布
排班与考勤               发布排班                  未授权
成员与党务               人工修正考勤              不可配置：超出委派上限
宣传与档案
知识与文件               搜索 / 仅看已授权 / 仅看改动 / 重点影响

当前显示：工作稿。已发布配置仍在生效。
新增 3 项，撤销 1 项，影响 12 个账号       取消本地修改  保存工作稿  预览发布
```

每项操作展示业务名称、覆盖动作、必要依赖和不可配置原因；技术码放入展开详情，不占主要阅读位置。一期范围展示为“本组织，仍受作者／指派及业务状态限制”；没有额外对象约束的操作可显示“本组织”。

区分三种状态：未保存的本地修改、已保存但未发布的工作稿、当前已发布配置。“取消本地修改”恢复最近服务器工作稿，不删除别人保存的工作稿；若需要放弃服务器工作稿，使用独立动作和版本校验。

切换角色、离开页面、关闭抽屉均提示处理未保存修改。只读账号查看已发布配置，不能因存在工作稿而误认为已生效。

权限配置状态分为：有效、待发布、领域包未启用、领域包授权需重新确认、超出可授权上限、角色失效；不要把不同原因合成一个“不可操作”。受保护角色允许阅读，但操作禁用并给出处理路径。

### 6.3 使用人员与角色替换

展示使用人员、所属部门、账号状态和管理身份标识。角色替换入口同时保留在用户详情，复用同一预览流程。

预览显示姓名和角色名称、增加／减少的操作、重点影响操作、当前生效范围；避免只展示用户或角色 ID。只允许选择启用且完整可分配的角色，不可分配原因可查询。岗位或邀请引用在独立区域展示，角色停用前能直接定位阻塞项。

一期仍做单用户替换；批量迁移角色留待二期。停用已有用户引用的角色时给出待处理清单，不强制清空账号权限。

### 6.4 发布预览

预览以“新增、撤销、范围变化、重新确认领域包授权”分组，显示操作中文名、前后配置、受影响账号数、其中有效账号数，以及岗位／未过期邀请引用。分页查看人员，统计由后端计算。

发布前显示重点变化，例如“新增组织排班发布权，影响 12 个账号”或“撤销成员导出权，影响 3 个账号”。保存草稿不触发权限生效；空差异不重复发布新版本。

继续使用五分钟有效预览，展示到期时间。发布绑定组织、操作者、角色、草稿与授权基线版本；确认时重新鉴权。版本变化需重新预览，保留本地输入供对比，不允许盲目覆盖。

网络超时后先按变更 ID 查询结果，再决定重试；同一变更重复提交只产生一个业务结果。发布成功刷新本页权限和人员数据，并通知其他会话更新当前授权状态。

### 6.5 管理身份与变更记录

所有者可查看管理员列表、有效期和可授权内容摘要，再进入委派详情。保存／撤销有清晰差异和确认结果；普通管理员只看本人委派。

变更记录提供时间、操作人、动作、对象筛选和分页；详情展示前后差异、发布版本及变更原因。记录身份名称快照以便账号停用或角色改名后仍可解释，不能仅依赖当前用户列表临时拼名称。

一期开放成功治理变更记录及必要拒绝原因记录，避免审计日志保存密码、设密凭证、完整个人敏感信息或业务正文。审计导出和历史配置恢复不在一期；历史查看不能一键覆盖现有授权。

### 6.6 有效权限解释

一期提供“选择用户 → 查看当前业务角色、有效操作、治理身份、配置未生效原因”，并展示与操作者自身权限无关的授权来源。

对重点流程提供对象级校验：策划审核、排班发布、考勤修正、材料读取。返回“缺少操作权限／不是指定审核人／业务状态不允许／文件敏感权限不足”等结论，不返回无权读取的资源正文。组织管理员的诊断能力不意味着可以打开目标人的所有业务资料。

通用任意资源诊断和模拟任意用户操作留待二期；一期不提供代登录功能。

## 7. 数据范围的后续设计

### 7.1 范围语义

| 范围 | 语义 | 典型适用对象 |
| --- | --- | --- |
| `ORG` | 当前组织内，不增加节点过滤，保留业务关系和状态限制 | 当前一期配置 |
| `SELF` | 业务定义的本人账号关系，不能一律理解为创建人 | 本人排班、考勤、课表 |
| `ASSIGNED` | 通过可信账号 ID 明确指派给本人 | 指派任务、指定审核 |
| `UNIT` | 账号明确关联的组织节点 | 成员、部门排班等 |
| `UNIT_TREE` | 明确节点及其下级节点 | 负责多层级组织的管理角色 |

范围按操作定义支持清单，不是所有模块都能选所有范围。`SELF` 与 `ASSIGNED` 不构成大小关系；范围编辑不能仅用一个数字比较宽窄。读取范围应覆盖该操作的写入对象，导出范围不得大于读取范围。

一期的本人入口和指定审核人规则继续在业务服务中落实，不等于已支持在角色编辑器任意配置 `SELF/ASSIGNED`。

### 7.2 开放条件与缺失归属处理

当前迁移虽有 `activity.owner_unit_id`、`task.assignee_user_id` 预留列，但对应实体尚未完整接入；任务仍有姓名文本，活动组织者也有文本字段。不能凭已有列或姓名猜测出可信归属。

二期先确定账号与组织架构节点的稳定关系，统一部门与组织节点口径，再回填活动归属、任务指派和文件来源。重名、空姓名、转部门、历史离职等情况必须进入待核对清单。

新增窄范围配置遇到归属缺失时拒绝或不可见，并给管理员修复入口，不回退全组织。存量 ORG 授权保持其明确的已发布范围，不因归属缺失被偷偷缩小；切换范围要预览影响并重新发布。

迁移与数据修复未通过之前，页面不提供节点范围下拉框。节点转移、指派变更和人员离职后，列表、详情、导出、统计、灵思、知识库和附件需同步采用新的可见范围。

## 8. 灵思、知识库与其他入口的一致性

1. 灵思工具与页面使用同一业务操作判断。创建任务依赖 `task:manage`，策划起草依赖 `plan:edit`，发布公告依赖对应公告权限，排班生成依赖 `schedule:generate`；读工具按实际结果所需权限及字段过滤处理。
2. 工具可见性、生成预览、确认执行、失败重试、任务恢复、成果编辑和历史成果读取均重新检查当前身份、对象关系与权限。不能只替换工具目录上的权限声明。
3. 人工确认不能替代权限。只读模式继续禁止写入；待执行任务受原授权上限与当前权限共同约束，后续新增权限不扩大旧任务能力。
4. 业务稿件、策划、材料等知识源使用同一来源鉴权规则。`kb:read` 只表示有知识库入口，`kb:restricted:read` 也不能越过成员、党务或策划来源权限。
5. 权限变更后，旧引用、检索历史、知识全文、统计、任务成果和附件直链均按当前权限重新验证；不可见数据不进入模型上下文。
6. 工作台、活动详情、搜索和通知按子模块权限裁剪。分页总数和统计在过滤后计算，不先把全量数据返回浏览器。
7. 撤权从后续请求、后续输出及尚未提交的业务动作生效；已开始提交的事务按真实结果返回回执，不宣称能撤回已经提交或已经下载的内容。
8. 权限更新事件只携带组织及版本等必要信息，客户端重新获取自己的有效权限；失去权限的按钮、菜单、弹窗同步更新。事件推送失败时由请求时校验和重新拉取兜底。

## 9. 逻辑模型与接口调整方向

### 9.1 数据模型

| 对象 | 设计变化 |
| --- | --- |
| `permission` | 增补业务分组、职责说明、风险提示、显式依赖、生命周期和替代码；治理、业务、基础能力分开呈现 |
| `sys_role` | 保留组织内角色和状态；补充能可靠维护的来源及修改元信息 |
| `role_grant` | 一期继续存已发布业务权限和 ORG 范围；二期范围参数通过版本化结构扩展 |
| `role_revision` | 保留工作稿与不可变发布快照；明确目录版本、依赖校验结果和发布说明 |
| `org_authorization_change` | 扩充差异、引用／人员影响摘要与查询回执；统计与预览绑定同一基线 |
| `org_role_delegation` | 一期复用固定治理预设与明确可授权清单；补委派预览，不偷偷启用任意治理能力编辑 |
| `org_audit_log` | 补结构化差异、对象类型和名称快照、变更关联 ID，支持筛选分页 |

目录中的同前缀字符串不再充当全部依赖定义；一个权限是否支持某范围由该操作实际实现的策略决定。逻辑描述、服务端执行与前端目录来自同一份版本化定义，避免三套独立列表。

### 9.2 接口契约

沿用现有 `/roles`、工作稿、预览、应用、有效权限和审计接口，在兼容期补充字段，不为页面重构直接废弃已有调用。

- 角色列表：搜索、状态、工作稿筛选、分页和摘要字段。
- 角色详情：当前发布配置、工作稿、版本、当前允许动作和逐项不可操作原因。
- 权限目录：业务中文分组、覆盖动作、依赖、范围、重点影响标记、可授权状态和明确原因码。
- 角色影响：使用账号、有效账号、岗位及邀请引用，支持分页及一致的聚合统计。
- 变更预览：中文差异、范围及领域包变化、影响、到期时间、版本；统一用于角色发布、角色分配和管理员委派。
- 有效权限：分别返回已配置、实际有效及失效原因；重点对象校验只返回最小可解释结果。
- 审计：筛选、分页、前后差异；避免每次加载全部用户只为把 ID 换成姓名。

错误需区分：登录失效、无此操作权限、对象不存在或不可见、业务状态不允许、版本冲突、预览过期和执行结果待核对。前端按错误语义处理，不把所有失败都静默吞掉或提示“保存失败”。

## 10. 存量授权迁移策略

### 10.1 不允许直接按旧权限名称批量扩权

先生成组织级迁移报告：角色、使用人数、治理身份、旧操作实际可达路径、新权限映射、可能减少或增加的能力、待人工核对项。显式授权和作者关系产生的既有能力都要检查，不能只复制 `role_grant` 的码。

| 旧配置／行为 | 拟迁移处理 |
| --- | --- |
| `activity:edit` 的现有职责集合 | 按实际路径映射活动编辑／阶段、任务、策划编写提交、议程和评分；保留作者及状态规则；后续由所有者拆分职责 |
| `activity:review` | 转为 `plan:review`，补必要读取依赖，保留指定审核人要求 |
| `schedule:manage` | 映射草稿维护、已有发布和导出能力、已有可用的生成能力及课表管理；列出迁移后的完整明细 |
| `schedule:check` | 收敛为本人打卡；不因旧放行分支自动授予人工修正考勤 |
| `attendance:manage`、`checkin:manage` 的修正能力 | 保留显式考勤管理授权作为候选，旧干事种子与交叉放行产生的能力单列，必须由所有者确认谁应保留；正式收紧前解决名单，不能默默剥夺或继续误授 |
| `content:manage` | 按既有管理能力展开为推文各职责，不越过业务状态；已有作者身份产生的操作另核对，缺少显式新操作时加入待确认迁移清单 |
| `news:manage` | 拆出当前已有的稿件维护和发布能力 |
| `kb:manage` | 拆出文档维护与索引管理，维持来源访问限制 |
| `schedule:view/free_table` 及个人入口 | 为既有合法用户补齐相应本人操作权限，分别核对课表与组织无课查询，不直接互相推导全组织权限 |
| 已有管理员可授权清单 | 同步迁移拆分关系，绝不能因新码缺失导致现有管理员无法维护原职责；敏感新增职责单独确认 |

新增依赖必须按原来合法可达行为补齐或列为待确认，不能借“自动补依赖”扩大可读数据。基础通知能力的目录退出要保留历史记录，运行时仍裁剪通知内容。

### 10.2 切换步骤

1. 导出旧授权快照、有效角色／委派／所有者清单及迁移报告，在隔离环境演练新增 Flyway 迁移。
2. 加入新目录和兼容映射，执行影子判定比对，不改变线上有效行为；未知、扩大或收紧项列入差异清单。
3. 由所有者核对考勤人工修正、宣传作者操作、导出、敏感权限及治理上限，形成明确迁移结果。
4. 切换新的统一判定与页面配置，整体更新组织授权版本；待确认授权和灵思写入预览失效并要求重新生成。
5. 新权限生效后，旧聚合码只能用于读取历史／迁移追溯，不允许“旧码或新码任一满足”长期共存。
6. 验收通过后再清理兼容写路径，保留历史快照与审计依据。

若切换失败，按经过演练的应用与授权快照方案回退；授权开始由新目录编辑后，不直接把旧版本覆盖回库，以免丢失新授权或恢复已撤销能力。真实 MySQL 数据迁移需单独验收，不能以 H2 通过代替。

- 统一前端入口、后端服务、文件、灵思、知识库、聚合和历史读取；完成当前在线会话的权限更新处理。
- 迁移报告与影子对比、角色和委派共同迁移、真实数据库演练。

一期按“目录与后端 → 页面和预览 → 跨入口接入 → 迁移验收”分批交付；每批都能独立评审，最后完成整体切换。任何未接入的细分权限不得提前开放给管理员配置。

### 二期：另行确认资源范围与治理增强

- 先完成可信账号／节点关联和数据回填，再逐模块开放 SELF、ASSIGNED、UNIT、UNIT_TREE 编辑能力。
- 从本人任务、部门排班、成员范围等明确场景开始，所有列表、导出、知识和附件同步接入。
- 开放细分管理预设、角色白名单、批量迁移和更完整对象诊断。
- 历史版本恢复以“生成新工作稿 → 预览发布”实现，不直接回写旧有效投影。

### 验收场景

| 场景 | 期望结果 |
| --- | --- |
| 管理员有可授权权但没有该业务读取权 | 可以配置职责，无法查看对应业务正文 |
| 只保存角色工作稿 | 业务访问和其他在线账号权限均不改变 |
| 只具备任务操作权 | 可处理授权任务操作，不能编辑活动基础信息或审核策划 |
| 有策划审核权但未被指定 | 列表、详情、审核、附件、灵思和知识来源均服从当前策划读取规则；不能审核 |
| 仅本人打卡 | 可登记本人合法班次，不能查看全组织考勤或人工修正他人记录 |
| 只具备自动排班生成权 | 可生成草稿，不能发布；页面与灵思一致 |
| 宣传编辑没有审核权 | 可执行授权编辑／提交动作，不能通过管理分支或 Agent 审核 |
| 关闭领域包后重新启用 | 旧批次不自动恢复授权；页面指出需重新确认 |
| 普通管理员操作受保护账号／共享角色 | 提前提示需所有者处理，后端仍拒绝越权请求 |
| 发布时其他人改动了工作稿或委派 | 原预览失效，保留输入并要求重新检查 |
| 发布网络超时后重复确认 | 能查询真实结果，只产生一次发布和一个有效结果 |
| 收紧权限后访问旧会话、成果、引用、导出和附件 | 使用当前权限检查，不靠旧缓存继续读取 |
| 撤权时已有动作开始提交 | 后续动作拒绝，已提交动作保留真实回执，不重复执行 |
| 迁移旧干事考勤权限 | 明确列出原有效能力及确认结果，无静默扩权或无说明收权 |
| 手机端编辑大量权限 | 分组、筛选、工作稿状态和固定操作区域可用，未保存改动有保护 |

后续测试包含服务端集成、权限依赖与迁移映射回归、前端交互和真实浏览器联调；重点验证低权限直接调用、跨组织访问及绕过页面的操作路径。本阶段仅提交方案，没有运行或宣称这些测试已经通过。

## 12. 本轮需要确认的业务决定

| 待确认项 | 建议默认方案 | 选择的影响 |
| --- | --- | --- |
| 本次实施边界 | 先完整交付一期；二期节点／指派范围另行评审 | 一期能解决职责混绑和页面可理解性，避免在数据归属未完成时承诺部门隔离 |
| 业务角色模型 | 继续单业务主角色，允许组合模板创建独立职责角色 | 不引入多角色合并、冲突和个人例外授权规则 |
| 普通成员考勤权限 | 本人打卡／本人记录；人工修正明确委派给考勤核验职责 | 旧干事授权需所有者核对，属于明确的业务边界调整 |
| 活动和宣传操作拆分 | 按第 4 节实施；审核、发布、导出与日常编辑分开 | 需要同步改业务接口、页面与灵思工具，不能只改权限表 |
| 管理身份 | 继续与业务角色分离，一期保留组织管理员预设 | 不把指导老师／主任等职位自动认定为系统管理员 |
| 当前策划和灵思隐私边界 | 保留作者、指定审核人、任务发起人及来源权限规则 | 本次重构不扩大管理员对业务正文和他人会话的读取能力 |

用户已确认本方案并授权一期实施；实施中的映射、取舍、验证结果与后续范围见[一期落地记录](PAMS-权限管理-v2-落地记录.md)。本节保留评审时的业务决定，实际交付以落地记录为准。
