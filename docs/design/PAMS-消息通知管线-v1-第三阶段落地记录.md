# 消息通知管线 v1：第三阶段首批落地记录

日期：2026-10-29

状态：治理个人告知、公告受众与独立确认、通知管线运维已实现；本地验证，未部署生产。第三阶段其余业务接入见末节。

## 治理告知

角色正式发布、启用、停用、归档、个人角色分配、管理员委派/撤销，在成功应用变更时通过审计挂点发出事务事件。工作稿保存、预览与重复 apply 不生成新的个人告知。

通知事件在 BEFORE_COMMIT 进入现有 Outbox，和授权变更一起提交/回滚。角色变更的受影响账号在生效时展开，个人身份变更通知目标账号；当前具有 `org:audit:view` 的治理者收到最小化摘要。受影响治理者只收个人通知，避免同一次变更收到两份。

新增 `GOVERNANCE_CHANGED` 类型，不可关闭即时提醒。可读性只依赖有效组织身份和冻结受众，不要求业务资料权限；正文不包含权限清单、内部原因或敏感业务内容。现有权限 WebSocket 刷新保持运行，个人收件箱和 SSE 负责可靠告知，二者职责独立。

## 公告受众与确认

新增 V53：公告重要标志、是否需要确认、确认版本及 `announcement_receipt`。通知接收人可选择组织内全部可查看公告的账号、指定人员或部门，与发布时的 `notice:view` 权限取交集；明确排除发布人。新页面显式选择通知范围；历史调用方不传范围时兼容组织受众。

公告正文继续依当前公告查看权限开放，通知受众不作为正文访问控制。这一点在发布表单中提示。普通公告静默入箱；重要或需要确认的公告允许即时提醒，仍尊重公告通知偏好。通知链接携带公告 ID，直接聚焦详情。

确认受众在发布时冻结，后来加入组织或获得角色的人不会继承旧的确认义务。当前接口分别提供：

- `GET /api/announcements/{id}/confirmation`：仅本人、本轮确认状态。
- `POST /api/announcements/{id}/confirm`：携带版本，当前受众且仍具有公告查看权限才可确认，重复确认幂等。
- 原公告已读和通知已读接口只更新阅读状态，不签收、不清除确认待办。

需要确认的公告修改正文或切换确认要求，必须作为重要更正重新发布。更正通过行锁串行增加版本，产生新一轮受众与确认记录；旧版本签收保留历史，旧页面提交的确认返回冲突。删除或撤销确认要求后不再列入个人待办。

工作台、通知中心、灵思共用的 `PendingWorkService` 新增公告确认事项；灵思引用和通知入口均定位到同一公告详情。知识库发布索引事件继续保留，并标记通知已由新入口处理，避免旧监听器再次广播。

## 管线运维

通知中心新增“管线运维”视图，仅当前组织有 `org:audit:view` 的治理者可访问。后端再次校验有效身份、当前组织和实时治理权限。

- `GET /api/notifications/operations`：Outbox、在线唤醒、定时提醒的状态计数、最早待处理时间、重试记录数、最近 50 条失败记录。
- `POST /api/notifications/operations/{outbox|delivery|reminder}/{id}/retry`：仅 FAILED 状态允许重新入队；限定当前组织及白名单表，清理旧租约、重置尝试次数。重复请求返回冲突。

页面只显示处理元数据和脱敏错误类别，不暴露消息正文、收件人资料或异常堆栈。不把在线唤醒成功描述为用户已收到或已阅读。重新入队后仍由原消费者校验业务有效性并依靠原有唯一约束保持收件箱幂等。

## 后续边界

本批没有将第三阶段整体标记完成。素拓/党务的本人通知仍依赖本人账号关系与本人可读接口；授权经办人的受控业务摘要、知识库索引故障与导入批次结果通知尚待接入。维护责任人配置、聚合告警、重试操作独立审计和更多延迟/去重指标也待补齐，当前先提供日志之外的组织内运维查询和失败恢复入口。

外部渠道、通用规则编辑器、多实例共享唤醒延续已评审的后续边界。上线前仍需生产 MySQL V50—V53、存量数据和完整 Nginx/CDN SSE 流式链路验证；本轮数据库集成验证使用 H2，未执行生产迁移或部署。
