## 集成验证中新发现并修复的问题

1. 创建活动的 type 在工具契约中可省略，但数据库要求非空。现在按 OTHER 处理，并在预览中显示，旧清单提交也有同样兼容。
2. 确认任务的批量状态更新未清理 JPA 一级缓存，持久化成功后仍可能返回 PENDING_CONFIRM。抢占与终态更新现在先 flush 再清理缓存，回执读取真实状态。
3. 表单审计使用 WRITE_INPUT，超过 side_effect 的 10 字符列限制。改为 INPUT，避免补参审计静默丢失。
4. 协作确认事件延后到 Run 快照与聊天消息保存之后发布，避免用户在快照落库之前确认、随后又被旧等待状态覆盖。

## 首批交付时的执行边界（第二批已扩展）

首批继续采用每轮一张确认清单。遇到待补或待确认动作后，串行执行暂停，不会假定尚未创建的业务实体已经存在。P2 计划包含可见写能力时暂按串行处理，避免并行预览相互取代清单；只读分支仍可并行。

确认后会保存真实业务回执并收敛整体状态；尚未执行的后续步骤仍保留为未完成。**本批未实现确认后自动续跑、版本化多清单共存、持久化 DAG 调度和节点租约恢复。** 这些属于下一批 S2。

停止检查覆盖专家循环与步骤边界，但没有实现模型传输级取消；S3 的 requestId、关键事件 outbox、断连补拉、缓存 TTL 与服务重启恢复也尚未交付。

审查本批只修正误判与表述，不宣称具备独立事实核验和语义质量审查。ReviewIssue、成果版本、差异比较和完整任务工作台仍待 S3/S4。

台账和通知等路径已纠正，但全量对象筛选/定位、所有能力的真实模型输入质量及各组织定制配置仍需逐项验收。

## 第二批：S2 执行内核（2026-10-24）

### 已实现

| 能力 | 具体行为 |
|---|---|
| 持久化任务 | 新增 AgentWorkItem，保存依赖、状态、修订版本、尝试次数和确认任务关联；AgentStep 在执行前创建尝试记录，完成后结算，同节点重试保留旧尝试 |
| DAG 调度 | 校验编号、依赖存在与无环；仅 SUCCESS 上游允许下游启动。默认最多并行 2 个就绪节点，可配置 `pams.agent.max-parallel-nodes`，有效范围 1–4；使用独立虚拟线程执行，不向原调度池提交子任务后阻塞等待 |
| 多清单 | 协作清单绑定 WorkItem 和 revision，兄弟分支互不作废。普通单 Agent 仍兼容原来的“新清单替换旧清单”，且不会误取消协作清单 |
| 确认后续跑 | 业务回执和节点结算事务提交后派发续跑；成功动作返回的真实实体 ID、业务引用与上游事实进入后续专家上下文。等待某个分支时，其他独立就绪分支照常执行 |
| 定点重试 | 仅重试没有 ActionTask 的 FAILED/PARTIAL 节点。任何已经提交业务动作的节点，包括提交结果 FAILED/PARTIAL，均禁止按模型节点重新写入；成功祖先不重放 |
| 局部修订 | 携带目标 revision 修改节点说明，同时递增该节点及传递下游的版本、撤销受影响的旧待确认清单；独立分支不变；分支已有业务提交时拒绝修订，避免把已产生的副作用当成可回滚状态 |
| 并发保护 | Run 调度令牌防重复驱动；确认保留后端 CAS；ActionTask 增加乐观版本，迟到表单不能覆盖取消/修订结果。修订与确认共用 Run 行锁，旧版本不能穿透确认 |
| 恢复 | 浏览器刷新从消息关联 Run 恢复全部清单与节点；显式继续会核对持久化业务回执。调度令牌超过 30 分钟允许人工触发恢复，未产生业务动作的中断尝试标为失败后手动重试；存在 RUNNING 业务提交时拒绝猜测结果和重复执行 |
| 权限与留存 | 续跑重新加载身份和组织，校验原始权限仍有效；新增权限不扩大既有 Run 的能力；原始只读模式跨恢复保留。上游输入执行出网过滤，非 normal 输出不复制进 WorkItem/Step 明文；聊天历史读取 Run 也复核权限 |
| 最小 UI | 同一轮展示全部待确认/待填写动作，各自显示结果；可查看节点依赖、修订版本和尝试次数，可定点重试、修订并继续。任务事件在聊天停止流式输出后仍能刷新所属 Run；旧请求不能覆盖新快照或其他会话 |

### 数据与接口

- 新增 `V43__agent_work_items.sql`：WorkItem 表、Run 的流/原始模式/权限快照/调度令牌，ActionTask 的节点/版本/留存级别/乐观锁，Step 的节点/尝试/修订版本，消息的 run_id。
- 兼容 V32 的既有 task.run_id；旧 Run 保留旧版详情，不推造历史依赖。JSON 字段使用明确的 JDBC JSON 映射，读侧兼容旧包装数据，避免跨事务反复读写产生多层字符串包装。
- `GET /api/agent/team/runs/{id}` 返回新 Run 的 nodes/actions 权威快照。
- 新增 `POST .../runs/{id}/resume`、`POST .../runs/{id}/nodes/{nodeId}/retry`、`POST .../runs/{id}/nodes/{nodeId}/revise`；修订请求为 `{revision,instruction}`。
- 协作入口可通过 toolMode 指定原始工具模式，mode 保留原有 P1–P4 标签兼容；生产执行以持久化依赖为准，旧标签不再代表强制绕过依赖的四套执行算法。
- `AGENT_RUN_UPDATED` 是刷新提示，Run REST 快照才是状态来源；前端按 Run 合并，不追加重复结果消息。RUNNING 时保留轻量补拉。

| 审查门禁 | BLOCKING 问题使清单进入 REVIEW_REQUIRED，不签发可用确认令牌；修订使旧清单失效，重新执行对应分支。WARNING 可继续人工核对。规则降级、无效 JSON、空审查、超长/受限输入均显示 UNVERIFIED，不宣称质量通过 |
| 旧审查兼容 | 旧执行器的“存在非空文本”结构检查改为 UNVERIFIED，不再返回 PASS，也不据此自动重放业务动作 |
| KB 实际输入 | 截断后的不可变片段副本同时用于 prompt 与引用映射；记录实际输入的来源、chunk、字符范围、截断标记、数据截至时间和 SHA-256。完整输入集合元数据写入检索日志，引用携带对应片段元数据，不另存一份敏感原文 |
| 请求身份 | 前端发送前生成 requestId，后端持久化请求归属、授权版本与 stream/conversation/run 映射；同请求重复受理被拒绝。支持首个事件之前取消，并保留取消标记阻止迟到请求开始执行 |
| 事件隔离 | 普通事件附 requestId；专家事件附 WorkItem/revision/attempt 与 task 通道。前端过滤其他窗口请求，任务正文不拼入最终答复；分片去重并按序号恢复正文 |
| 可靠事件 | Run 状态变化与带 eventSeq 的 outbox 元数据在同一事务提交；投递使用可到期租约、令牌和重试，发送失败不确认投递。数据库事件仅含状态与归属，正文 token 保留于有界短期缓存 |
| 可靠续跑 | 确认后的低延迟内存通知保留，持久事件补偿丢失的唤醒；启动及定期扫描修复节点/动作回执不一致。旧进程中断的模型尝试留为可手动重试；可能已提交的动作标记 NEEDS_RECONCILE，禁止自动重复写入 |
| 停止传播 | 关闭模型 HTTP/SSE 连接并取消模型工作线程，停止排队的工具与后续节点，普通及协作的待提交清单均失效；取消后的模型调用不再重试或降级。已开始的业务提交不被强制打断，显示 STOPPING，随后保留真实成功/失败回执及整体部分完成状态 |
| 取消历史 | 已创建会话的取消请求保存一条简洁停止回执，刷新或重开后仍可见；首帧前且未建立会话的取消不创建空会话 |
| 重连恢复 | 订阅建立后先取请求/Run/消息快照，再拉游标之后的事件；缓存缺失或截断明确要求快照。请求或会话已切换时丢弃迟到响应，较旧 stateVersion 不回滚新状态；当前请求失败恢复与协作运行使用有界轮询兜底 |
| 缓存生命周期 | 流事件、序号、所有者、授权版本、取消标记、身份映射和推理暂存随流清理；流缓存有数量上限和活跃/结束 TTL，已淘汰流的迟到推送不会重新创建缓存。前端去重窗口也设上限 |
| UI | 审查问题直接显示位置、引文与修订建议，一键打开对应步骤编辑；阻断正文可展开阅读。停止、需修订、结果待核对都有明确文案；桌面浅色、手机深色和历史滚动行为均做浏览器回归 |
