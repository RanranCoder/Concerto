## 目标场景

用户打开某活动策划书，说“只把预算改成 3000 元，其余内容保留”。灵思读取明确版本，生成可核对的修改建议；用户查看差异并确认后创建新草稿。原版本、未修改部分及可支持的格式保留。若期间有人保存了新版本，系统要求重新基于最新文档生成，禁止覆盖。

## 关键技术决策

1. **先验证 DOCX 修改机制。** 用包含表格、编号、页眉页脚的样本，验证当前编辑器/文档处理通道能否精确修改目标内容。未通过前，不承诺任意文档格式保真，也不静默退化为纯文本覆盖。
2. **并发基线必须真实有效。** 先核对现有版本与文件保存语义，再选择 revision、内容指纹或其他可靠令牌；仅传版本 ID 未必能识别同一草稿被再次保存。
3. **长文限制形成显式契约。** 不直接删除 24000 字符限制。定义读取、审查与写入预算；超预算明确说明并阻止不完整全文修订。分段审查作为后续增强。
4. **部分采用后置。** N05 首版完成可信差异与整份采用；逐段采用需额外处理编号、表格和引用依赖，在核心闭环验收后另估 2–4 人日。
5. **测试围绕真实失败模式。** 重点覆盖并发保存、越权读取、重复确认、进程恢复和文档字节；模拟 API 页面测试与真实业务联调分别记录。

## 里程碑与实施顺序

- **M1：基线可复现。** 完成 N01、N02；梳理源码、验收记录、实际部署和迁移历史的对应关系。仅检查和记录，不自动执行生产迁移。
- **M2：原文可准确读取。** 完成 N03、N06 与 DOCX 修改技术验证，确定支持的修订范围。
- **M3：修订闭环交付。** 完成 N04、N05、N07；用独立 MySQL、真实模型小样本及浏览器验证“读取→修改→差异→确认→Word 保存→恢复”。

若按约三个工作周推进，优先保证 M1、M2，再按技术验证结果承诺 M3。发布门槛是原稿不变、目标修改准确、并发冲突可阻止、重复执行无副作用，以及约定范围内格式保留。
